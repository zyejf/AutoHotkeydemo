# 可运维性 / 生产就绪度评估 — ASD 技能管理器 v4.0

> 评估人：雷克斯（Rex）· SRE 工程师
> 日期：2026-09-19
> 评估对象：`D:\1demo\AutoHotkeydemo`（主 worktree，分支 `main`）
> 定位前提：**个人用户的 Windows 桌面工具**（无服务端、无集群、无值班团队）。本评估不套用 SaaS 运维标准，只判断一件事：**它出问题时能不能被看见、被定位、被恢复**。

## 证据口径声明

- 本文所有「实测」如未特别说明，**均为本机（Windows + Git Bash）实跑**，不是 CI。
- CI 侧运行记录本轮**不可得**：实测 `gh auth status` → `You are not logged into any GitHub hosts`（本机）。团队负责人早先核对的 96 次运行记录本轮无法复核，本文不引用其为「实测」。
- 每条发现附 `文件:行` 或实跑命令输出。凡未实跑验证的，显式标「推断」并给出验证方法。

## 1. 本域结论

**不达标（就「可运维性」单一维度，建议 No-Go），但距离「接近生产级」只差一组小而确定的改动。**

一句话说明：**底层进程治理（watchdog / JobObject / 原子写盘）写得比多数同类桌面应用更扎实，问题全部出在「故障信号到不了用户眼前」这一层** —— 执行器崩溃后热键静默全失、配置损坏静默回退默认值、热键注册失败不落盘日志、紧急恢复热键从未被实现，四者叠加，使一个「崩溃后自动重启」的系统在用户端表现为「莫名其妙就不好使了，且无从查起」。加上 release 构建路径从未真正执行过，当前**既发不出去，也退不回来**。

判定依据不是"缺少 Prometheus/Grafana"（那对单机桌面工具本就不该要求），而是下面这三条对本项目成立的最低门槛都没过：

1. **核心功能失效时，用户能看到吗？** → 不能（发现 B1-1，阻断）
2. **用户报错时，我们能拿到可用的现场吗？** → 只有一半（有版本+日志目录，无日志包导出、AHK 侧零日志、热键失败不落盘）
3. **出问题时，能退回去吗？** → 不能（release 路径未验证 + 无 updater + 无版本共存）

## 3. 事故响应预案批判性审阅（D1）

审阅对象：`deliverables/engineering-assurance/full-review-and-incident-response-2026-09-19.md` §4（行 154-236）、`incident-git-ref-loss-drill-2026-09-19.md`。

### 3.1 总体判断

这份预案**作为一份"工程审查报告的附属章节"是合格的**——它的自我认知很清醒（每处缺口都标了"当前无"、"待补"），故障模式 F1/F2/F3 的归纳也准确（本轮 A/B 两组发现基本都落在 F1/F2 里，说明归纳有效）。

但它**作为一份"可执行的事故响应预案"是不合格的**，原因不在于写得不好，而在于**它被写成了一份 SaaS 预案**：默认存在"值班团队、监控告警、分级升级、对外通报"这套组织装置。对一个"作者一人 + 用户若干、无服务端、无监控"的个人桌面工具，这套装置**不存在，且不该被建立**。照它执行时，响应者会在第 4.1 步（检测与告警）就卡住——没有任何一条动作是当前能做的。

### 3.2 逐项判定：可执行 / 纸上谈兵

| 章节 | 内容 | 判定 | 理由 |
|---|---|---|---|
| §4.0 三种故障模式 F1/F2/F3 | 归纳首现症状与影响面 | **可执行 ✅** | 准确且有用。本轮发现 1/3（F1）、发现 4/8（F2）均落在其中。建议保留，并补一条 **F4：安装/启动失败**（发现 19 的 WebView2、发现 5 的打包资源缺失），这是分发后最可能先炸的场景。 |
| §4.1 检测与告警 | 崩溃检测、关键指标、告警渠道、CI 健康度 | **纸上谈兵 ❌** | 四项全部是"现状无 / 待建立"。其中"关键指标（IPC 断连次数、watchdog 重启次数…）"**对单机桌面工具不成立**——没有聚合端，指标无处可去。这一行应整体删除，不要留成待办（留着会让人以为哪天要建一套指标系统）。 |
| §4.2 影响面评估 | 判定受影响版本/功能/数据/可否绕过 | **半可执行 ⚠️** | "判定受影响版本"整行建立在 release 产物之上，当前不可执行（发现 5）。"判定受影响功能（查日志）"、"判定可否绕过"可执行。 |
| §4.3 定级与升级路径 | SEV1/2/3 + 升级路径 + 响应时限 | **纸上谈兵 ❌（需重写）** | "30 分钟内响应"、"4 小时内"对**无值班团队**的项目是空话——没人值班，时限约束不了任何人。且升级路径（工程负责人 → 全员）在单人项目里是自我升级。**建议改为按"用户能否绕过"定级**，见下方建议。 |
| §4.4 止血与回滚方案 | 重启/恢复备份/重装/统一兜底 | **半可执行 ⚠️** | "重启应用"、"从 `backups/` 恢复"、"删除配置回默认"都可执行（但发现 8 指出**大概率没备份**）。"回滚上一版"当前不可执行（发现 5）。最后的"🔴 关键缺口"自述准确，予以确认。 |
| §4.5 沟通通报与值班分工 | IC / 技术处置 / 验证 / 沟通 四角色 + 通报模板 | **纸上谈兵 ❌（需重写）** | 四角色映射到"工程保障团队现有职能"——但那是**审查阶段的团队**，不是**事故时刻的值班团队**。事故发生时大概率是作者一人面对一条用户消息。"对外通报"没有"外"（无用户列表、无状态页）。通报模板里"影响范围：待补——缺用户规模数据"对单机工具**永远补不上**，应删掉该字段。 |

### 3.3 具体增删建议

**删（对本项目不成立，删掉比留成待办更好）：**

1. **删"关键指标"整行**（§4.1）——无聚合端，指标无处可去。
2. **删 SEV 的"响应时限"列**（§4.3）——无人值班，时限无意义。
3. **删通报模板的"影响范围"字段**（§4.5）——单机桌面工具永远填不出"多少人受影响"，留着只会每次都写"待补"。
4. **删"升级路径"**（§4.3）——单人项目不存在升级。

**改（保留骨架，换成对个人桌面工具有效的判据）：**

5. **SEV 改为按"用户能否自救"定级**，这是单机工具唯一有意义的标尺：

   | 级别 | 判据（本系统） | 处置 |
   |---|---|---|
   | **SEV1** | 核心功能全失（F1/F2）**且用户无绕过方案**（重启无效、无备份、无旧版可退） | 立即修，发新版 |
   | **SEV2** | 核心功能失效但**有绕过方案**（重启可恢复 / 有备份可还原 / 可回默认配置） | 排期修，先给用户绕过步骤 |
   | **SEV3** | 非核心缺陷、性能退化、日志/文档问题 | 正常排期 |

   注：本轮的发现 1+3（执行器死后热键静默全失、且重启不恢复）按此判据正好是 **SEV1**——用户既看不到原因，重启也不一定有效。

6. **"检测与告警"整章改为"用户反馈回路"**，只保留三件当前可做的事：
   - 用户怎么找到我们 → **缺失**，对应发现 9（补 issue 模板）
   - 用户能给我们什么 → **半有**，诊断页版本+日志目录（发现 11 待补导出）
   - 我们怎么知道 CI 是否健康 → **缺失**，对应发现 16（`gh auth`）

7. **"值班分工"改为"事故时的三个动作"**（一个人按顺序做完即可）：
   1. 让用户贴诊断页内容 + 出问题时段的日志文件（告诉他是哪个文件，注意发现 13 的 UTC 日期坑）
   2. 按 F1–F4 归类，按上面新判据定级
   3. 能绕过就先给绕过步骤，不能绕过就修 + 走 release job 发新版

**增（本轮发现暴露、预案里没有的）：**

8. **增 F4「安装/启动失败」故障模式**（发现 19 WebView2 离线、发现 5 打包资源缺失）。这是分发后**最先**会遇到的，预案里完全没有。
9. **增一条"用户侧排障动作清单"**（给用户的，不是给作者的）——因为本项目没有值班团队，最有效的"止血"是**让用户自己绕过**。当前用户能做的只有"重启"，而发现 14 指出"重装"对本应用无效但看起来有效，必须明确写清：
   - ✅ 有效：重启应用
   - ❌ 无效：卸载重装（配置不会清除，问题依旧）—— 见发现 14
   - ✅ 有效但需要入口：恢复默认设置 / 从备份恢复 —— **入口目前不在 UI 上**（发现 14/15）
10. **增一条"回滚窗口"的硬约束**：release 产物当前只作为 CI artifact 保留 90 天（发现 18），预案里所有"退回上一版"的说法都隐含"上一版还在"。应在预案中写明：**事故距发布超过 90 天时，回滚能力已自动失效**，必须新建 Release 而非依赖 artifact。

### 3.4 对 `incident-git-ref-loss-drill` 的简短意见

该演练文档（git ref 丢失演练）**与本评估的可运维性靶点相关度低**，它演练的是**开发期仓库事故**，不是**用户侧运行事故**。它本身没问题，但不应与 §4 混为一谈——两者的事故类型、影响面、响应者完全不同。建议在新预案里把它明确标为「开发期事故」，与「用户侧运行事故」分开成两个预案，避免响应者拿错剧本。

## 6. Go/No-Go 建议（仅就可运维性维度）

### 结论：**No-Go**

不因为"缺少企业级运维体系"（本项目不该有），而因为下面四条**按本项目自己的定位也成立**的底线未过：

1. **核心功能失效时用户看不到**（发现 1）——执行器死后界面一切正常，用户无从得知。
2. **配置损坏时表现为"数据丢了"且无通知**（发现 4），**且大概率没有备份可恢复**（发现 8）。
3. **既发不出去也退不回来**（发现 5 + C7）——release 路径从未执行，无历史产物，无 updater。
4. **没有任何反馈回路**（发现 9）——没有服务端监控的前提下，检测能力为零。

### 放行条件（按性价比排序，前四项做完即可从 No-Go 转 Go）

> 这四项都是**小而确定**的改动，不涉及架构，合计工作量远低于本轮已完成的任何一项重构。

| 优先级 | 动作 | 对应发现 | 为什么是它 |
|---|---|---|---|
| **P0-1** | 诊断页增加「执行器状态」显示 + 「重置执行器」按钮（直接复用现成的 `getExecutorStatus()` / `resetWatchdog()`，前端封装都已写好，只差调用） | 1, 2 | 成本极低（两个已有 API 各加一次调用），却直接把"静默全失"变成"可见可自救" |
| **P0-2** | 配置加载失败时弹对话框告知 + 提示"可去备份页恢复" | 4 | 把一个"用户以为数据永久丢失"的最坏体验变成"有明确指引的临时降级" |
| **P0-3** | `save_config_atomic` 前自动备份当前配置（保留最近 10 份） | 8 | 一行调用 + 一个清理循环，让发现 4 的恢复路径真正有东西可恢复 |
| **P0-4** | 手动触发一次 release job，人工盯全程并记录实际结果 | 5, C1 | 不跑一次，"能发布/能回滚"就永远是假设。**建议放在 P0-1~3 之后**，否则会锁定一个已知缺陷的基线 |
| P1-1 | 热键注册/注销失败加 `tracing::error!` | 6 | 最核心故障补上现场证据 |
| P1-2 | `.github/ISSUE_TEMPLATE/bug_report.yml` + 诊断页"前往反馈"按钮 | 9 | 建立唯一的检测回路 |
| P1-3 | 按 §3.3 重写预案 §4.1/§4.3/§4.5，增 F4 | D1 | 让预案从"写得对但不适用"变成"照着能做" |
| P1-4 | 实测确认"执行器重启后热键是否恢复"（检查项 B5），若否，加重放逻辑 | 3 | 决定 watchdog 的自动重启对用户到底有没有价值 |
| P2-1 | 诊断页"导出日志包 / 打开日志目录" | 11 | 补上现场获取链路最后一步 |
| P2-2 | 版本号统一到单一权威源（TD-078） | — | 否则事故时"哪个版本"这个字段永远是错的 |
| P2-3 | AHK 侧加本地日志 | 7 | 补上最需要现场那一侧的空白 |
| P2-4 | 实现或移除 `CONTROL_HOTKEYS.emergency`（F10） | 10 | 要么真能用，要么别让人以为有兜底 |
| P2-5 | release 产物挂 GitHub Release（而非仅 90 天 artifact） | 18 | 解除回滚窗口的隐性上限 |

### 一句话给决策人

**这个项目的"抗崩溃"做得比"可排障"好得多**：进程死了能自动拉起来、不留孤儿、写盘不写坏，这些都对；但拉起来之后功能没回来、用户也不知道发生了什么、我们更收不到任何信号。补齐"故障信号到用户眼前"这一层（P0-1~P0-4，都是小改动），可运维性即可达到"接近生产级"；**在补齐之前发布，等于把"用户说不清、我们查不到、双方都退不回"的三无状态交付给真实用户。**
