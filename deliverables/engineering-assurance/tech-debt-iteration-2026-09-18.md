## 一、本轮已落地

### 1.1 TD-051：图谱 JS 依赖提取（Archi）

把 JS 边改成**互斥穷尽的四分法**：

| 类别 | 内容 | 是否进环检测 |
|---|---|---|
| value | 普通 `import` | ✅ |
| **type-only** | `import type X from` / `import { type X } from`（全部绑定都带 type）/ `export type { X } from` | ❌ |
| **re-export** | `export { x } from` / `export * from` / `export * as ns from` | ✅ |
| builtin | `node:` 前缀 | ❌ |

- **仅类型边不进环检测**：`import type` 编译后被完全擦除、不产生运行时依赖，把它当真实依赖会让无害的类型循环被判成真环并硬失败阻断提交。
- **重导出是此前的假阴性**：`export { x } from` 整体漏检。它是货真价实的依赖（模块会被执行、符号被转发），现已计为值边并参与环检测。
- 新增 `build_graph.py --selftest`（用例表覆盖仅类型 / 重导出 / 阴性三类）+ 闸门 `check_js_edge_taxonomy`：拿 `js.edges` 独立重算环检测输入，与图里留痕的 `js.cycle_input_edges` **对撞**——防「守护在跑但跑的是自己的输出」这类永真式。
- **基线零漂移**：`counts` 一字未改，新增 `js_type_only_edges=0`、`js_reexport_edges=0`（本仓无 TS、无重导出）。

**阳性对照用了「新旧行为同注入复算」的对照法**（不是只看改后有没有报警）：

| 注入 | 新行为 | 旧行为复算 |
|---|---|---|
| `import type { invoke } from './tauri.js'` | 36 边 / 环 0 | **37 边 / 环 1** ← 证明原实现确实会误判 |
| `export { invoke } from './tauri.js'` | 51 边 / 环 1，闸门 FAIL 并点名两文件 | 禁用识别后 50 边 / 环 0 ← 假阴性坐实 |

> ⚠️ **我下发的前提有一条是错的，已被 Archi 纠正**：我依据旧报告认为 e2e 目录被 `extra_exclude` 整体排除、JS 依赖完全不在图里。实测 `js_e2e_files=19` **已在图内**，该盲区在 TD-051 前半就修掉了。我已核实基线 `scope` 字段的记载，确认他的纠正成立，故该项**不再追加**。

### 1.3 C10：防漂移守卫 + G3i 接入（Cody）

- **C10 三处门禁档位一致**（硬失败、不做棘轮），双探针：G3d 的 `--no-cargo` 有无、G3i 的 `--selftest` 有无。
- 两个刻意设计：
  1. 判据每次从三份文件**正则提取后互比**，脚本里**不存**「标准清单」——否则那份清单就成了第五份权威副本，与本检要消灭的漂移是同一类错误。
  2. 判定用「**标志有无**」而非「调用命令全文」——三处 shell 语法天然不同（G3c 就是现成反例：`.sh` 用通配、`.ps1` 用 `Get-ChildItem`，语义等价文本不同），比全文必然全是假阳性。
- **G3i**（`build_graph.py --selftest`）接入三处，紧挨 G1，且**刻意不进 `--quick` / `-SkipGraph`**——自检类闸门被跳过即等于不存在。
- 阳性对照是**端到端真跑**：破坏重导出正则 → `bash scripts/check-gates.sh` 真的 FAIL、结尾 `FAILED GATES: G3i`；还原 → 全绿。

> ✅ Cody 主动**否决了 C10 的通用化**，论证成立：做成「任一闸门调用命令必须一致」会因语法差异全是假阳性；做成「闸门 ID 集合齐备」一上就红（G3g 只在 `.sh`/`ci.yml`、G3f/G3h 只在 `ci.yml`），压下去又要维护豁免清单——**而豁免清单正是 C10 要消灭的假权威副本**。

### 1.4 E2E：通道第一次真正开火（Rex）

**执行序列（修正后）**：

| 次序 | run id | commit | 结论 | 关键事实 |
|---|---|---|---|---|
| 1 | `35309066359` | — | failure | 零用例执行（死因④：e2e 未装依赖、`npx wdio` 静默降级废弃 `wdio@6.0.1`） |
| 2 | `35310528367` | `e53d136` | failure | 9 spec 全挂、`ECONNREFUSED`（死因⑤） |
| 3 | **`35312497783`** | `ce78fb1` | failure | **42 分钟**——此前从未被记录，本轮捞出 |
| 4 | `35327797606` | `ce78fb1` | failure | `Spec Files: 0 passed, 9 failed, 9 total in 00:36:32` |
| 5 | `35333326568` | `cce526f` | 待定 | 本轮为拿探测数据而触发 |

**第四次执行的关键证据**：

- wdio 汇总行原文：`Spec Files:	 0 passed, 9 failed, 9 total (100% completed) in 00:36:32`
- 9 个 spec **确实派发了**（日志有 9 条 `RUNNING in wry` + 9 条 `FAILED in wry`），但**零用例执行**——全部死在建 session 之前
- 错误原文：`WebDriverError: Request timed out! ... when running "http://127.0.0.1:4444/session" with method "POST"`
- **算术交叉验证**：每个 spec 恰好 4 分钟 = 4×60s（`connectionRetryTimeout:60000` × `connectionRetryCount:3`），9×4=36m32s，与汇总行完全吻合

**第五道死因修复确认生效**：诊断日志 `[OK] msedgedriver.exe 存在: ...\asd-tauri\e2e\drivers\msedgedriver.exe`；失败形态从 `ECONNREFUSED`（连不上）变为「连得上但无响应」（tauri-driver 已绑定 4444）。

**第六道死因**：tauri-driver 接受 TCP 但 `POST /session` 永不返回。Rex **拒绝推断根因**——`wdio.conf.js` 原只在 `waitForPort` **失败**的 FATAL 分支落盘 driverLog，而这次 `waitForPort` **成功了**，所以 driver 的 stdout/stderr 一行都没留。

**已做的可观测化改造**（`cce526f`）：
- `driverLog` 提到模块级（原为 `onPrepare` 内的 `const`，`onComplete` 根本看不见）→ `dumpDriverLog()` 无条件落盘 + 尾部打印进 CI 日志
- 建会话前加三行探测：`msedgedriver --version` + WebView2 Runtime 的 HKLM/HKCU 两处注册表键
- `connectionRetryCount` 3→0：无效等待 36 分钟 → ~2 分钟

> ✅ 我独立核实了 Rex 的假设①前半段：`ci.yml` 里 WebView2 **只出现在第 31 行的描述文字中**，全 workflow 无任何安装步骤。⚠️ 但这**不等于**运行时缺失——`windows-latest` 镜像通常预装 Edge/WebView2。这正是那行探测存在的意义：**把猜测变成事实**。
