# 按键触发时延实测报告（精确定刻优化）

- 日期：2026-09-13
- 范围：**periodic + sequence + enhanced_\*（hybrid）**，即 `sender.ahk` 全部周期/序列类调度路径
- 指标口径：**「计划时刻 → 抬起完成」的 P95 ≤ 20 ms**（含 `keyPressDuration`，默认 15 ms）
- 目标：低时延 **且不漏发按键事件**

---

## 1. 结论速览

| 场景（interval / kpd） | 优化前 P95 | 优化后 P95 | 优化前 最大 | 优化后 最大 | 判定 |
|---|---|---|---|---|---|
| 100 ms / 15 ms | 16.2 ~ 26.8 ms（5 轮中 **3 轮超标**） | **14.8 ~ 15.0 ms** | 30.95 ms | **15.03 ms** | 达标 |

### 1.1 推广到 sequence / enhanced_*（hybrid）

| 模式 | 场景 | 优化前 P95 | 优化后 P95 | 优化前 步进 | 优化后 步进 |
|---|---|---|---|---|---|
| sequence | `[F1,F2]` / delay=100 / kpd=15 | **248 ~ 263 ms** | **14.97 ms** | 111.93 ms（应为 100） | **100.000 ms** |
| hybrid | periodic 子组 100 ms + sequence 子组 150 ms | 未单独基线（与 sequence 同源缺陷） | — | — | F1 周期 100.010 ms；F2/F3 交替 299.974 ms（= 2 × 150） |

hybrid 下所有按键保持时长 14.98 ~ 15.00 ms；同一时刻到期的 F1+F2 **都**拿到了完整的 15 ms
（验证「批量 Down → 统一等待 → 批量 Up」生效，见 §4.3）。

同时修正了两项正确性缺陷（详见 §4）：

- **周期保真度**：100 ms 间隔下，优化前实测周期中位 **95.2 ms**（系统性地快 5%）、最大 111.7 ms；优化后中位 **100.000 ms**、最大 100.03 ms。
- **漏发/吞发**：优化前在滞后时会把时间基准重置为当前时刻，既丢相位又吞掉本应发生的触发；优化后改为**保相位单调推进**，并对跳过的周期计数。

## 2. 瓶颈定位（实测，非推测）

### 2.1 排除的怀疑项

| 怀疑项 | 结论 | 依据 |
|---|---|---|
| 防抖 / 节流 | **不存在** | `sender.ahk` 无任何 debounce/throttle 逻辑 |
| DOM 操作 | **不在链路内** | 前端仅在 `main.js` 做日志展示，不参与按键触发闭环 |
| 回调链深度 | 不是瓶颈 | 链路只有 `SetTimer → _ExecutePeriodic → _SendKeyDown` |
| 合并窗口 | 不适用 | `sender.ahk` 没有单次触发 API，periodic 为唯一路径 |

### 2.2 真实瓶颈：Windows 15.625 ms 定时器网格

本机实测（AutoHotkey v2）：

| 机制 | 实测结果 |
|---|---|
| `A_TickCount` 步进 | 中位 **15.52 ms** → 根本无法度量 20 ms 以内的时延 |
| `SetTimer` 周期 / `Sleep` | 锁死在 **15.625 ms 网格**；请求 1/5/10/15 ms 均得到 ~15.6 ms；**请求 16 ms 反而得到 ~31 ms**（跨格跳 2 格） |
| `timeBeginPeriod(1)` | 对 AHK **完全无效**（调用后 `SetTimer(1ms)` 仍为 15.68 ms） |
| 一次性 `SetTimer(-1)` 自轮询 | 主线程空闲时中位 **15.67 ms**，不存在亚 15.6 ms 的唤醒手段 |
| **QPC 忙等** | 目标 20 ms → 中位 20.0017 ms，**误差 0.0017 ms** |

因此：**AHK 内唯一可用的精确定刻手段是 QPC（QueryPerformanceCounter）**。
这同时也否定了「把调度下沉到 Rust」的方案——`executor.ahk:17` 的 `SendLevel(10)` 与
`hotkey_hook.ahk:54` 的 `InputLevel(11)` 决定了 Rust 侧 `SendInput` 会被 AHK 当作**物理按键**
（物理按键触发所有 level）→ 自触发死循环。

### 2.3 优化前的时延构成

```
计划时刻 ──(等待 SetTimer 唤醒：0 ~ 15.6 ms 网格误差)──▶ _SendKeyDown
          ──(SetTimer(-kpd) 释放：0 ~ 15.6 ms 网格误差)──▶ _SendKeyUp  ← 抬起完成
```

两处网格误差叠加，且旧实现的 `threshold = interval - Max(1, Round(interval * 0.05))`
允许**提前 5% 触发**，导致周期系统性地偏离配置值。

## 3. 优化措施

1. **新增 QPC 高精度时钟** `ahk_executor/high_res_clock.ahk`
   - `Now()`：QPC 毫秒时间戳，分辨率远优于 1 ms。
   - `SleepUntil(target)`：三段式等待 —— 剩余 > 50 ms 用粗 `Sleep`（留 40 ms 安全边界）
     → 中段 `DllCall("kernel32\Sleep", "UInt", 0)` 让出 → 末段 1 ms 纯忙等。

2. **重写 `_ExecutePeriodic`**：建立 QPC 基准 → 求最近到期时刻 → 提前唤醒 + `SleepUntil` 精修 →
   到期才发送。不再依赖「轮询 + 阈值判定」。

3. **保持时长精确定刻** `_PressPrecise()`：`Down → SleepUntil(plannedAt + kpd) → Up`，
   当 `kpd ≤ PRECISE_HOLD_MAX_MS(20)` 时启用；超过则退回异步释放（该配置下必然 > 20 ms，精确定刻无意义）。

4. **保相位单调推进**（修漏发）：基准从**本次触发的计划时刻**推进，而非发送完成后的当前时刻。
   原实现 `if triggerTimes[i] < now - interval then triggerTimes[i] := now` 会重置基准。

5. **唤醒提前量 `WAKE_LEAD_MS = 28`**（实测选参，见 §5.2）。

6. **同一套策略推广到 `_ExecuteSequence` / `_ExecuteHybrid`**：
   子项统一表示为 `[kind, grpIdx, idx, dueAt, params, key, keyCount]` → 取最近 `dueAt` →
   提前唤醒 + `SleepUntil` 精修 → **按 `dueAt` 分桶批量发送** → 用 `dueAt` 保相位推进基准。
   enhanced_* 只是 `_ExecuteHybrid` 的薄封装，改造自动覆盖。
   `StartSequence` 的 `nextStepTime` 初始化为 **0**（而非调用时刻），基准改为在**首次执行**时确立 ——
   否则定时器首次回调可能晚到 100 ms 以上，首步 `dueAt` 已过期，会直接跳过一步。

## 4. 修正的缺陷

### 4.1 漏发 / 吞发（正确性）

`sender.ahk:382`（旧）在滞后时把基准直接改写为 `now`：

```ahk
triggerTimes[i] := triggerTimes[i] + interval
if triggerTimes[i] < now - interval
    triggerTimes[i] := now          ; ← 既丢相位，又吞掉本应发生的触发
```

改为保相位推进，并对跳过的周期计入 `state["droppedTriggers"]`，使漏发**可观测**而非静默。

### 4.2 周期系统偏移 5%

旧实现允许提前 5% 触发，实测 100 ms 配置下周期中位只有 95.2 ms。
优化后周期中位 100.000 ms。

### 4.3 同刻多键被串行化，第二个键保持时长塌成 ~0

按到期时刻分桶前，`_ExecutePeriodic` 对同一时刻到期的多个键逐键执行
「Down → 等待 → Up」，第二个键开始等待时 `plannedAt + kpd` 早已过去 → 保持时长塌成 **0.022 ms**
（实测 F1=14.97 ms / F2=0.022 ms）。改为**按 `dueAt` 分桶 → 批量 Down → 统一等待 → 批量 Up** 后，
F1/F2 均为 14.96 ms。

### 4.4 sequence 首步被跳过（推广时新发现）

`StartSequence` 原先把 `nextStepTime` 初始化为**调用时刻**，而定时器首次回调可能晚到 100 ms 以上，
导致首步 `dueAt` 已过期：按下立即返回（保持 0.033 ms），且 `next <= now` 被误判为「已落后」而白跳一步，
实测 F1 → F3，**F2 整个丢失**。改为 `nextStepTime := 0` + 首次执行时确立基准后，
F1 → F2 → F3 依次为 99.975 / 99.999 ms，保持均 14.99 ms。

## 6. 已知限制

1. **短间隔下保持时长可能被压缩**：`_PressPrecise` 以「计划时刻 + kpd」为抬起目标，
   若按下本身迟到（定时器抖动），保持时长会短于 kpd。实测 interval=20 / kpd=15 这类
   占空比 75% 的极端配置下，最小可到 0.03 ms。常规配置（interval ≥ 50）下最小 14.96 ms，无影响。
2. **精确定刻会连续占用 AHK 主线程**（本次实测，务必知悉）：
   等待期间 AHK 不泵消息循环，`SleepUntil` 的让出段用的是 `DllCall("kernel32\Sleep", 0)`，
   **不会**放行其它 AHK 定时器。
   实测方法：另挂一个 5 ms 探针定时器，统计其唤醒间隔。interval=100 / kpd=15 下：

   | 指标 | 实测 |
   |---|---|
   | 探针唤醒间隔 P50（即定时器网格本身） | 16.08 ms |
   | 探针唤醒间隔 P95 / 最大 | 43.98 / 47.47 ms |
   | **扣除网格后的最长连续占用** | **31.39 ms** |
   | 占用占空比 | **29.2 %** |

   后果：技能组运行期间，IPC 命令与热键最多被推迟约 **31 ms**（旧实现完全不阻塞主线程）。
   短间隔（interval < 50）下占空比还会更高。**这是用「单线程忙等」换「亚毫秒精度」的固有代价**，
   暂无无副作用的替代方案（`timeBeginPeriod` 对 AHK 无效、定时器锁死 15.625 ms 网格）。
   若将来需要兼顾，可考虑「多段提前唤醒」把单次连续占用压到 ~16 ms，但会多承担一次定时器抖动风险。
3. **`kpd > 20 ms` 不启用精确定刻**：该配置下「计划时刻 → 抬起完成」必然 > 20 ms，已无意义。
4. **宿主调度抖动无法从代码侧消除**：kpd 默认 15 ms，而预算是 20 ms，**可用余量只有 5 ms**。
   宿主（杀软、磁盘刷写、其它进程抢占）一次 > 5 ms 的抢占就会让该样本超标。
   实测在系统安静时 42 个样本全部落在 15.01 ~ 15.02 ms；系统繁忙时偶发 28 ms / 78 ms 离群。
   因此时延类断言必须按 P95 取足量样本，不能退化为「最大值」（见 §8）。

## 8. 时延类测试的统计口径（踩坑记录）

**坑：样本量太小时，P95 会退化成「最大值」。**
`_Pct(arr, 0.95)` 的索引是 `Ceil(n * 0.95)`；`n = 7` 时索引 = 7 → 断言的其实是 **P100**。
宿主只要抖动一次，用例就红。这曾让本轮改造在完整套件里偶发失败（观测到 77.70 ms / 28.37 ms），
而单独跑同一套件 9/9 全绿 —— 典型的「只在负载高时失败」。

处置：

| 断言性质 | 正确统计量 | 理由 |
|---|---|---|
| 端到端时延 P95 ≤ 20 ms | **P95 + 样本量 ≥ 40** | 需求就是 P95；`n = 42` 时索引 40，真正容忍 2 个离群 |
| 保持时长 == kpd | **P95 + 样本量 ≥ 20** | 同上，容忍个别离群 |
| 步进是否**漂移** | **中位数** | 漂移是系统性偏移，会把全部样本一起推走，中位数即可检出；宿主抖动只污染个别样本，不该让「漂移」用例失败 |

另外两条：

- **不要用 Map 存中间结果**：旧版 hybrid 用例把 `holds` / `steps` 存进 Map，
  同名键互相覆盖，最终只剩**最后一个**样本，等于单样本断言。必须收进数组。
- 观察窗口因此拉长（本轮 +9 s 左右）。为的是「P95 真的是 P95」，值得。
