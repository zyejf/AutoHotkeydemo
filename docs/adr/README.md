# 架构决策记录（ADR）

本目录存放本仓的**架构决策记录**。2026-09-19 之前仓内没有 ADR 目录，也没有既成命名规范 ——
本文件即规范本身，新增 ADR 请照此办理。

## 命名规范

```
docs/adr/ADR-<三位序号>-<短横线连接的小写英文短语>.md
```

例：`ADR-001-v3-ahk-stack-positioning.md`、`ADR-002-hotkey-merger-merge-semantics.md`

- 序号**三位补零**、全局递增、不复用（ADR 只增不改：结论变了就**新立一条并在旧条顶部标注被取代**，
  不要就地改写历史决策 —— 与台账「历史数字不得就地改写」同一条规矩）。
- 短语用英文、小写、短横线连接，控制在 2~5 个词，要能一眼看出决策对象。

## 必备章节

每条 ADR 至少包含六节，顺序如下：

| 节 | 要回答的问题 |
|---|---|
| **状态 / 日期 / 决策人 / 关联** | 当前是 Proposed 还是 Accepted？谁定的？对应哪条审查发现或台账 ID？ |
| **背景** | 现状是什么、**已实测的证据是什么**。⚠️ 凡声称「某机制存在/不存在」必须给文件取证或命令输出，不得推断 —— 本仓当天已三次因「靠推断写结论」返工。 |
| **选项分析** | 至少两个备选方案，按复杂度 / 成本 / 可扩展性 / 风险逐项评估，并给出**不推荐项的否决理由**。 |
| **决策** | 选了哪个、为什么，以及**明确的边界**（本次做什么、不做什么）。 |
| **后果** | 分**正面 / 负面 / 需要重新审视**三段。负面必须写，包括「本次没有解决什么」。 |
| **复审触发条件** | 列出可判定的条件（出现什么信号就复审），而不是「定期复审」这种不可判定的表述。 |

若决策附带后续代码改动，另加「**后续实施步骤**」表（步骤 / 内容 / 是否改变行为）——
ADR 本身是**文档决策**，代码改动必须单独立项排期，不在同一轮里夹带。
