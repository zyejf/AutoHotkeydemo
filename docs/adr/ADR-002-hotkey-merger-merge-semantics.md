# ADR-002: HotkeyMerger 的合并语义（节流 vs 事件流）

**状态:** Proposed
**日期:** 2026-09-19
**决策人:** 系统架构师（阿奇）· 待工程督导复核
**关联:** 全仓代码审查 #11（HotkeyMerger 合并语义未决策）；台账 TD-068

---

## 背景

`asd-tauri/crates/asd-ipc-protocol/src/hotkey_merger.rs`（131 行，其中生产代码 56 行）负责把
AHK 子进程上报的热键事件做「合并」后再交给上层。当前实现的形态是：

```rust
const HOTKEY_MERGE_WINDOW_MS: u64 = 100;

pub fn push(&mut self, msg: IpcMessage) {
    let hotkey = msg.keys.as_ref().and_then(|k| k.first()).cloned().unwrap_or_default();
    if hotkey.is_empty() { return; }
    self.buffer.insert(hotkey, msg);        // ← 同键直接覆盖
}

pub fn flush(&mut self) -> Vec<IpcMessage> {
    self.last_flush = std::time::Instant::now();
    self.buffer.drain().map(|(_, v)| v).collect()
}
```

### 已实测的事实（不是推断）

1. **语义未声明，但实现是 last-write-wins 的节流（throttle）**
   - `buffer` 是 `HashMap<String, IpcMessage>`，`push` 用 `insert` —— 同一身份键在窗口内的
     后续事件**静默覆盖**前一条，窗口结束时只剩最后一条。
   - 既有测试 `test_hotkey_merger_same_key_overwrite` 已经把这一行为钉成了「预期」：
     push 3 条 seq=1/2/3 的 F1，flush 只得到 1 条且 `seq == 3`。
     **即：当前语义是事实上的节流，但代码与文档都没有写明「为什么是节流」**。

2. **被吞掉的事件完全不可观测**
   - 全文件**没有任何日志、计数或返回值**暴露「本次丢弃了几条」。
   - `push` 返回 `()`，`flush` 返回剩余消息 —— 丢弃数量、丢弃的 seq 集合都无法追溯。
   - 后果：若某类热键（典型如 **toggle 类**：开/关两个状态靠连续两次事件表达）在 100ms 内被触发两次，
     第二次覆盖第一次，**上层只看到「关」或只看到「开」**，表现为「按了没反应」或「状态反了」，
     而日志里什么都查不到。

3. **身份键只取 `keys[0]`，与 AHK 侧可变参构成潜在契约断点**
   - Rust 侧构造器：`IpcMessage::hotkey_event(seq, hotkey)`（`message.rs:129`）**只接受单个热键**，
     `keys` 恒为长度 1 的数组。
   - AHK 侧构造器：`IpcClient.SendHotkeyEvent(keys*)`（`asd-tauri/src-tauri/ahk_executor/ipc_client.ahk:494`）
     是**可变参数**，`"keys", keys` 可以是多元素数组。
   - **实测当前唯一生产调用点** `hotkey_hook.ahk:129` 传的是单键 `normalizedKey`，所以
     多键形态**目前未在生产中被触发** —— 这是**潜伏**断点，不是已发生的缺陷。
     一旦将来有人用它发一次多键事件，Rust 侧 `keys.first()` 会把整条消息的身份收敛成第一个键，
     而消息体里仍带着全部键 → 身份与载荷不一致。

4. **`should_flush` 只看时间窗，与缓冲区内容无关**
   `last_flush.elapsed() >= merge_window && !buffer.is_empty()` —— 窗口是**固定节拍**，
   不是「静默 N 毫秒后才发」。因此「节流」这个词的常见含义（首次立即发、之后限速）**不成立**，
   当前实现更接近「每 100ms 采样一次最新值」。

---

## 选项分析

### 选项 A：明确为**节流（throttle / 采样）**语义 —— 维持 last-write-wins

| 维度 | 评估 |
|------|------|
| 语义 | 「窗口内同键只保留最新一条」，上层关心的是**当前状态**而非**事件序列** |
| 复杂度 | Low（即现状） |
| 行为变更 | **无** |
| 适用场景 | 状态型热键（按下/释放、模式开关）—— 只关心「现在是什么」 |
| 风险 | **toggle 类事件语义错误**：两次事件叠加成一次，状态可能反了 |
| 可观测性 | **必须补**（否则永远查不到被吞事件） |

### 选项 B：改为**事件流（保序不丢）**语义 —— 窗口内同键事件全部保留

| 维度 | 评估 |
|------|------|
| 语义 | 「窗口内同键的事件按序全部下发」，上层关心的是**发生了什么** |
| 复杂度 | Med（`HashMap` → `HashMap<String, Vec<IpcMessage>>` 或 `VecDeque`） |
| 行为变更 | **有**：`flush()` 返回条数会变多，既有 5 条测试里有 2 条断言（「F1 只留 1 条」）会红 |
| 适用场景 | toggle 类、连击计数类 —— 每一次触发都有意义 |
| 风险 | 键盘连发/自动连发场景下事件量放大，上层处理成本上升；**可能引入新的性能与抖动问题** |
| 可观测性 | 天然可观测（不丢事件） |

### 选项 C：按事件类型分派 —— 状态型走节流、toggle 型走事件流

| 维度 | 评估 |
|------|------|
| 语义 | 精确，但需要知道「哪些是 toggle 型」——**当前 IPC 消息里没有这个信息** |
| 复杂度 | **High** —— 要先扩 `IpcMessage` 契约（AHK 侧同步改），再分派 |
| 风险 | High —— 跨语言契约变更 + 分类规则本身又是一处双真值 |
| 时机 | 依赖产品侧对「哪些热键是 toggle 型」的输入，当前**缺外部信息** |

---

## 决策

**采纳选项 A（明确为节流语义），并强制要求：被吞事件必须可观测。**

1. **语义定型**：`HotkeyMerger` 的语义是 **节流采样** —— 每 `merge_window` 毫秒，对每个
   身份键只产出**窗口内最后一条**事件。上层必须按「读当前状态」而非「读事件序列」来消费它。
   - 理由：① 这就是当前实现，选它**零行为变更**，不会打断既有 5 条测试与所有调用方；
     ② 现有调用方（热键上报 → 上层状态机）消费的是状态，没有发现需要事件序列的消费点；
     ③ 选项 B 会改变 `flush()` 的返回条数，属于**行为变更**，必须单独排期并评估连发场景的影响；
     ④ 选项 C 缺外部输入（无法判定哪些热键是 toggle 型），现在做是拍脑袋。

2. **被吞事件必须可观测（本次唯一允许的改动方向）**：
   在 `push` 里对「覆盖掉一条已存在事件」的情形计数，并通过 `tracing` 输出。
   **约束**：只加观测，**不改变任何行为**（不返回新值、不改 `flush` 结果、不改丢弃逻辑）。
   - 若实施，推荐形态：`tracing::debug!(hotkey = %hotkey, dropped_seq = %prev.seq, "hotkey 事件在合并窗口内被覆盖")`；
     若要能断言，则加一个 `#[cfg(test)]` 可见或 `pub fn` 的计数器。**计数器的公开会改 API 表面**，
     属代码变更，需单独排期——故本次**不改代码**。

3. **身份键 `keys[0]` 的契约断点，本次只登记不修**：
   - 目标形态：身份键应为「规范化后的完整 `keys` 序列」而非 `keys[0]`；
   - 前置条件：先与 AHK 侧对齐 `SendHotkeyEvent(keys*)` 的实际取值范围
     （实测生产唯一调用点是单键，多键形态尚未触发）；
   - 在对齐之前，在 `push` 的文档注释里写明「身份 = `keys[0]`，多键消息会被收敛」这一现状。

4. **本 ADR 是文档决策，本次不修改 `hotkey_merger.rs` 的行为**（改动合并语义属代码变更，需单独排期）。

## 后果

### 正面

- 「合并」到底是什么意思有了书面定义，不再靠读代码猜；
- 为「toggle 事件被吞」这类疑难问题提供了**可排查的入口**（要求可观测）；
- `keys[0]` 的潜伏契约断点被显式记录，不会被遗忘；
- 零行为变更，不打断既有测试与调用方。

### 负面

- **toggle 类事件的语义错误没有被修复** —— 本 ADR 只是明确了「当前是节流」，
  若上层真的需要事件序列，问题依旧存在；
- 「被吞事件可观测」在本次**未落地**（要求可观测 ≠ 已经可观测），落地需另排期；
- 选择节流意味着**永久放弃**窗口内的中间事件，若将来出现连击计数类需求，需要回到本 ADR 复审。

### 需要重新审视的部分

- 上层消费者对 `flush()` 结果的使用方式，需要按「状态读」而非「序列读」复核一遍
  （本次未做，属实施步骤）；
- AHK 侧 `SendHotkeyEvent(keys*)` 的可变参设计，与 Rust 侧单键构造器不对称，
  应在 IPC 契约统一时一并处理。

## 复审触发条件

出现任一情形即复审本 ADR：

1. 出现「热键按了没反应 / 状态反了」的实际用户反馈，且怀疑与 100ms 合并窗口有关；
2. 上层出现**需要事件序列**的消费点（连击计数、节奏判定等）—— 此时应改走选项 B/C；
3. AHK 侧开始用 `SendHotkeyEvent` 发送**多键**事件（潜伏断点兑现，S4 必须提前）；
4. IPC 契约统一工作启动时（`keys` 字段语义需一并敲定）；
5. `merge_window` 需要从 100ms 调整时（说明场景假设变了）。
