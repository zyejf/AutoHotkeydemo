# ADR-001: v3.0 AHK 栈的定位（转维护模式，冻结新功能）

**状态:** Proposed
**日期:** 2026-09-19
**决策人:** 系统架构师（阿奇）· 待工程督导复核
**关联:** 全仓代码审查 #24（双 UI / 双运行时栈配置不共享）；台账 TD-069

---

## 背景

仓库内**同时存在两套可独立运行的完整实现**，二者各有自己的配置真值位置、各自的校验器、各自的 UI：

| 维度 | v3.0 AHK 栈（仓库根） | v4.0 Rust/Tauri 栈（`asd-tauri/`） |
|---|---|---|
| 入口 | `main.ahk` / `asd.ahk` | `asd-tauri/src-tauri/src/lib.rs`（34 个 `#[tauri::command]`） |
| 架构 | DDD 四层（`infrastructure` 15 / `domain` 8 / `application` 3 / `presentation` 6） | 5-crate workspace |
| 规模 | 约 32 个生产 AHK 文件 / 11.4k 行 | `asd-domain` 3709 / `asd-application` 3754 / `asd-ipc-protocol` 948 / `asd-test-harness` 389 行 |
| UI | `presentation/app_ui.html` | `asd-tauri/index.html` |
| 配置位置 | `ConfigService.configPath := "config.json"`（**字面量**，AHK 默认解析为脚本工作目录） | `app.path().app_data_dir().join("config.json")`（`lib.rs:702-707`，取不到时**回退到当前目录 `config.json`**） |
| 配置校验 | `infrastructure/config_validator.ahk`（759 行） | `crates/asd-domain/src/validator.rs` |
| `AGENTS.md` 的定位 | 「v3.0 采用严格 DDD 四层架构，**作为独立运行模式保留**」 | 「v4.0 采用 5-crate workspace 架构，通过 IPC 管理 AHK 子进程」 |

### 已实测的问题（不是推断）

1. **配置真值位置分裂（#24 的直接证据）**
   - `application/config_service.ahk:26`：`static configPath := "config.json"` —— 相对路径，随工作目录变化。
   - `asd-tauri/src-tauri/src/lib.rs:702`：`app.path().app_data_dir()` + `config.json`。
   - 二者**只在「恰好从同一目录启动」时指向同一文件**。Tauri 打包运行时的 `app_data_dir` 通常是
     `%APPDATA%\<bundle-id>\`，与 AHK 脚本目录不是同一个地方 → **同一份用户配置存在两个副本**，
     在 A 栈里改的配置在 B 栈里看不到，反之亦然。
   - 更隐蔽的是 Rust 侧 `lib.rs:704-705` 的**回退分支**：取不到 `app_data_dir` 时静默使用
     `std::path::PathBuf::from("config.json")`（当前目录），于是「配置在哪」在不同运行环境下会变。

2. **活跃度已显著偏向 Tauri 栈**（`git log --since="30 days ago" --oneline` 实测）
   - AHK 生产目录（`infrastructure`/`domain`/`application`/`presentation`）合计 **10** 次提交；
   - `asd-tauri/` 合计 **83** 次提交。
   - 且 AHK 侧近期的提交**全是缺陷修复**（TD-047 降级默认配置不合法、`PovToDirection` 量纲 BUG、
     `_DebugLog` 隐式依赖、`_BridgeDeleteGroup` 返回值），**没有新功能**。这是「事实上已在维护模式」
     的客观信号——只是没人把它写成决策。

3. **两套校验器已实测存在结论分裂**（详见 ADR 关联的技术债 TD-067）：同一份配置在两侧会得出
   「Rust 判合法 / AHK 判非法」的不同结论，已实跑确认 **8 个分歧面**（对拍夹具覆盖 7 个，明细见台账 TD-067）。

4. **`AGENTS.md` 的定位描述是「保留」而非「发展」** —— 但「保留」不等于「维护模式」：
   现状下任何人都可以往 AHK 栈加功能，且没有文档说清「加在哪一侧」。

## 选项分析

### 选项 A：双栈并行演进（维持现状，不明确表态）

| 维度 | 评估 |
|------|------|
| 复杂度 | **High** —— 每条业务规则要在两侧各写一遍、各测一遍 |
| 成本 | **High** —— 双份实现 + 双份测试 + 双份文档；实测两侧已产生 7 处分歧 |
| 可扩展性 | Low —— 新功能要问「在哪一侧加」，答案随人而定 |
| 用户价值 | Low —— 用户只用其中一个 UI，双栈不产生叠加价值 |
| 风险 | **High** —— 配置双真值位置会静默分叉，用户「改了没生效」且不报错 |

### 选项 B：立即删除 AHK 栈

| 维度 | 评估 |
|------|------|
| 复杂度 | Low（删完就简单了） |
| 成本 | **一次性 High，且不可逆** |
| 风险 | **High** —— ① `AGENTS.md` 明确写了「作为独立运行模式保留」，删除是**改权威边界**，超出本次授权；
            ② AHK 栈承载摇杆/手柄（`joystick_*`）等能力的完整实现，Rust 侧没有对等物（见下「影响」）；
            ③ 11.4k 行生产代码 + 664~722 条 AHK 用例一次性作废，损失的是可运行的回归资产 |

### 选项 C（推荐）：AHK 栈转**维护模式**，冻结新功能，配置真值统一到 Tauri 侧

| 维度 | 评估 |
|------|------|
| 复杂度 | **Low** —— 只加一条定位约束，不改任何代码路径 |
| 成本 | Low —— 本次零代码改动 |
| 可扩展性 | Med —— 新功能一律进 Tauri 栈；AHK 栈只收缺陷修复 |
| 风险 | **Low** —— 可逆（随时重新解冻），不删除任何资产 |
| 遗留 | 配置双真值问题**未被代码修复**，只是明确了「以哪一侧为准」 |

---

## 决策

**采纳选项 C。**

1. **v3.0 AHK 栈（仓库根 `main.ahk` / `asd.ahk` 及其四层目录）自本 ADR 起进入维护模式**：
   - **冻结新功能**：任何新能力一律实现在 v4.0 Rust/Tauri 栈；
   - **允许且仅允许**三类改动：生产缺陷修复、既有测试接入/加固、安全与依赖问题；
   - **不做**为 AHK 栈新增的重构、架构调整、性能优化专项。

2. **配置真值以 Tauri 侧为准**：`app_data_dir/config.json` 是权威副本；AHK 栈继续使用
   `config.json` 相对路径**在本次不做代码改动**（改路径属于行为变更，需单独排期，见「后续实施步骤」）。
   在代码统一之前，**以文档口径先行**：AHK 栈与 Tauri 栈不应被同时用于编辑同一份配置。

3. **跨栈规则必须登记**：两侧任何共享业务规则（配置校验、IPC 布尔契约等）的分歧，
   一律登记到 `docs/tech-debt-register.md`，并优先用对拍测试钉住（见 TD-067 的做法）。

4. **本 ADR 不改 `AGENTS.md`** —— 权威边界的修订由文档负责人（Docu）统一处理口径。
   本 ADR 与 `AGENTS.md` 的关系是：AGENTS.md 说「保留」，本 ADR 把「保留」细化为
   「**保留但冻结新功能**」，二者不冲突。

## 后果

### 正面

- 「新功能加在哪」有了唯一答案，不再靠口头约定；
- AHK 栈的 10 次/月 提交里那些缺陷修复仍然是**允许的**，不会误伤；
- 为「配置真值统一」这项**真正的代码改动**提供了前置决策依据——先有定位，再谈迁移；
- 不删除任何代码，可逆，不触碰 `AGENTS.md` 权威边界。

### 负面

- **配置双真值位置仍然存在**，本 ADR 只是明确了以哪一侧为准，**没有消除分叉本身**；
  用户在 AHK 栈里改的配置在 Tauri UI 里仍看不到（反之亦然）。这是**已知且被接受的**遗留风险。
- AHK 栈若长期无新功能，其 664~722 条用例可能与 Tauri 侧逐步脱节，维护价值递减；
- 「维护模式」需要有人在执行时判「这是缺陷修复还是新功能」，存在边界争议（见复审触发条件）。

### 需要重新审视的部分

- 若 AHK 栈摇杆/手柄能力被确认为主力功能（台账「待定项」里挂着 `joystick / vJoy 是否主力功能`），
  则「冻结新功能」对摇杆方向可能不成立，需单独开 ADR；
- 若未来要**删除** AHK 栈，必须先解决：① `AGENTS.md` 权威边界修订；② 摇杆能力在 Rust 侧的对等实现；
  ③ AHK 回归资产（664~722 条用例）的去留。

## 后续实施步骤（不在本次范围，需单独排期）

| 步骤 | 内容 | 风险 |
|---|---|---|
| S1 | 将 AHK 侧配置路径参数化（支持环境变量 / 启动参数覆盖），使双栈可指向同一文件 | Med（改配置加载链路） |
| S2 | Tauri 侧 `lib.rs:702` 的 `app_data_dir` 回退分支改为**显式报错或显式日志**，消除「配置位置随环境漂移」 | Low |
| S3 | 评估「AHK 栈只读 Tauri 侧配置」是否可行（AHK 栈不再写盘） | High（AHK 栈当前是独立运行模式，会写盘） |

---

## 复审触发条件

出现任一情形即复审本 ADR：

1. 有人提出在 AHK 栈实现**新功能**（本 ADR 默认拒绝，需要复审才能放行）；
2. 摇杆/手柄（`joystick_*`）被确认为产品主力功能；
3. 出现「用户在 AHK 栈改配置、在 Tauri UI 看不到」的**实际用户反馈**（说明遗留风险已兑现，应提前 S1）；
4. `asd-tauri` 与 AHK 生产目录的 30 天提交数之比跌破 2:1（说明 AHK 栈重新活跃，定位需重定）；
5. 决定删除 AHK 栈（本 ADR 作废，改立删除 ADR）。
