# 方案 B · 平衡重构（推荐 · 收益与风险兼顾）

> 三份方案（A 保守 / B 平衡 / C 深度）按**激进程度**划分，选型指南见
> [`README.md`](./README.md)，全部量化依据见
> [`bench-report-2026-09-14.md`](./bench-report-2026-09-14.md)。
> 本方案包含方案 A 的全部任务，未重复展开的部分以「同 A」标注并给出增量说明。

## 0. 方案定位

**一句话**：在方案 A 的「单点安全替换」之上，**进入定时器热路径做一次有等价性验证的提速**，
同时把基准纳入 CI 防止收益被后续改动吃掉。

| 维度 | 说明 |
|---|---|
| 改动面 | 7 个文件、10 处改动；其中 1 处（T6）涉及定时器主循环 |
| 是否需要开关 | **T7 需要**（定时器策略，默认关闭）；其余不需要 |
| 预期周期 | 中等（热路径改动需要更充分的压测与灰度） |
| 适用场景 | 常规迭代窗口；团队能接受热路径改动；希望拿到 tick 路径的确定收益 |

**相对方案 A 的增量**：T6（tick 遍历合并）、T7（定时器策略，带开关）、T11（基准进 CI）。

**相对方案 C 不做的事**：不重写序列化层整体、不做定时器状态机化、不动模块边界。

## 1. 优化目标与判定指标

### 1.1 量化指标

耗时一律取 **p50**；CPU 类指标**必须跨轮可复现**才作为判据（见 §1.3）。

| 编号 | 指标 | 定义与测量方法 | 当前基线 | 目标 | 判定方式 |
|---|---|---|---|---|---|
| M1 | JSON 序列化耗时 | 2 KB 配置对象 p50 | **1.29 ms** | **≤ 0.10 ms**（≥ 90%） | `bench_json_escape` |
| M2 | 大字符串序列化耗时 | 8 KB 纯文本 p50 | **5.44 ms** | **≤ 0.30 ms**（≥ 90%） | 同上 |
| **M8** | **tick 处理耗时（8 键）** | 单次 tick 的 p50 | **31.7 µs** | **≤ 20 µs**（≥ 35%） | `bench_tick_traversal` |
| **M9** | **tick 处理耗时（24 键）** | 同上（大技能组） | **84.6 µs** | **≤ 50 µs**（≥ 40%） | 同上 |
| M3 | 异常守卫覆盖率 | 已知容错缺口被守卫覆盖比例 | **0/3** | **3/3** | `bench_stability` |
| M4 | 长跑内存残留 | 5 万次创建并丢弃后的私有内存 | **19.5 MB** | **≤ 1 MB** | `bench_cycle_leak` |
| M5 | CPU 占用率 | 8 组 × 100 ms 定时器风暴 | 20.7 ~ 25.0%（多轮区间） | **不劣化**（≤ 上限 + 2 pp） | `bench_timer_storm` |
| **M10** | **定时尾部误差 max** | 实际执行时刻相对计划时刻的最大误差 | 1.05 ~ 4.92 ms（跨轮摆动） | 仅当 T7 开启时：≤ 0.5 ms 且跨轮稳定 | 同上 |
| M6 | 启动时间 | 外部墙钟 | **164.33 ms**（empty，n=11） | **不劣化 ≥ 5%** | `tools/ahk-probes/bench_startup.py` |
| M7 | 回归基线 | AHK + Rust + 四闸门 | **见 test-map.md**（当前 697） | 不减少、不新增跳过 | `scripts/check-gates.sh` |

### 1.2 关于 T7（定时器策略）的指标口径 —— 必须读准

**不要把 T7 描述成「提升精度」。** 实测结论是：

- **p50 / p95 三者几乎无差别**（p50 0.072 → 0.074 ms，p95 0.145 → 0.145 ms）；
- 可复现的差异只有**尾部稳定性**：`new` 的误差 max 稳定在 **0.17 ~ 0.23 ms**，
  而 `old` 在 **1.05 ~ 4.92 ms** 之间大幅摆动（三轮一致）；
- **CPU 方面本机未测出可复现差异**：`old` 20.7~25.0%，`new` 23.4~28.9%，
  两个区间互相重叠，与同一变体自身的轮次波动同量级。

因此 T7 的立项理由只能是「**消除偶发尾部抖动**」，
**既不能拿「省 CPU」也不能拿「更耗 CPU」当理由**。这也是它必须带开关、默认关闭的原因。

### 1.3 统计口径（保留方案 A 的三条，并加一条）

1. 用 **p50** 判定，不用 max；
2. P95 只在样本量足够时用；判断漂移用**中位数**；
3. 结论必须**跨轮可复现**；
4. **（B 新增）** 涉及 CPU 的结论，必须给出**多轮区间**并显式检查区间是否重叠 ——
   重叠即视为「未测出差异」，不得写入收益。

### 1.4 非目标

不追求缩短启动时间、不追求序列化层再提速（那是方案 C 的 T9）、不做架构收敛。

## 3. 实施方案与风险评估

> T1 / T2 / T3 / T4 / T5 / T8 的实现路径与风险**同方案 A**（见
> [`plan-A-conservative.md`](./plan-A-conservative.md) §3）。以下只写 B 的增量任务。

### T6 · tick 遍历合并（P1）

**现状**：`_ExecutePeriodic` 每次 tick 对同一份按键表遍历 **4 次**
（`:454` 建立基准、`:461` 找目标、`:482` 收集到期、`:522` 算下次轮询），
并调用 **3 次** `_IntervalOf`（`:400-403`，每次都做一次 `interval < MIN_INTERVAL_MS` 判断）。
这段代码在定时器回调里，是 CPU 占用的主要来源之一。

**实现路径**：

1. 合并为**一次遍历**：边走边同时算出「最早到期时刻 / 到期数量 / 下次目标时刻」。
2. `_IntervalOf` 的结果在同一次遍历里复用，不再重复计算。
3. **等价性校验先行**：对 500 次迭代逐项比对新旧实现的
   `[target, dueCount, nextTarget]`，要求 `diffs = 0`。
   基准脚本里已经跑通了这一点（报告 §3.2：`diffs=0 IDENTICAL`），
   落地时把这段校验直接搬成单测。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| **合并后 `nextTarget` 语义不等价** | 走了「推进前的值」而非「推进后的值」 → 节拍漂移 | 等价性校验必须包含 `nextTarget`；基准第一版就是栽在这里 |
| 一次遍历里状态过多导致逻辑绕 | 可读性下降、后续维护出错 | 三个累加量用明确命名的局部变量，并保留旧实现作为注释对照 |
| 按键数极大时收益变化 | 基准只测到 24 键 | 压测覆盖 1 / 8 / 24 / 64 键 |

**兼容性影响**：对外无影响。内部循环结构变化，但输出（发送时机与顺序）必须逐项一致。

### T7 · 定时器策略改为忙等到点（P2，带开关）

**现状**：`sender.ahk:470-472` / `:529` / `:566` / `:596` 在距离目标时刻不足一个定时器网格时，
重排 `SetTimer(..., -Max(1, Round(target - now - WAKE_LEAD_MS)))`。
网格是 15.625 ms，所以 `Max(1, ...)` 会造成**反复唤醒**（实测 1.08~1.30 次唤醒 / 次工作）。

**实现路径**：

1. 新增配置项 `preciseBusyWait`（**默认 false**）。
2. 开启时：当 `remaining < 16 ms`，不再重排定时器，直接用 QPC 忙等到点。
3. 关闭时：行为与现在完全一致。
4. 默认关闭的依据是 §1.2 —— 收益只在尾部稳定性，且 CPU 影响不可复现。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| **忙等阻塞 AHK 主线程** | 期间其它定时器、热键、IPC 均被推迟 | 实测主线程最大停顿 29.2~30.7 ms，三变体同量级；仍需在压测中复核 IPC 响应时延 |
| 与既有 `SleepUntil` 语义叠加 | 可能出现双重等待 | T6 合并后只保留一个等待点，不允许存在第二个 |
| 默认关闭意味着代码长期未被真实流量覆盖 | 开关打开时可能踩到从未执行的分支 | 灰度阶段**必须开一轮开关全开**的验证 |

**兼容性影响**：默认关闭 → 无影响。开启后定时精度特征变化，需要在发布说明中写明。

---

### T11 · 基准纳入 CI（P1）

**现状**：`tools/ahk-bench` 目前是本地手动跑。若不在 CI 里跑，
T1 / T6 的收益会在后续改动中被悄悄吃掉，且没人第一时间发现。

**实现路径**：

1. 在 `.github/workflows/ci.yml` 增加 `bench` job（windows-latest），
   跑 `json_escape` / `tick_traversal` / `stability` 三项（**不跑** `timer_storm` 与
   `cycle_leak`：前者需要 12 秒且 CPU 结论不可复现，后者需要多进程且对 CI 噪声敏感）。
2. 判据用**相对阈值 + 宽容忍**：加速比低于历史值 50% 才失败
   （CI 机器负载不可控，过严会随机红 —— 项目里已经有 G3b 抖动误报的教训）。
3. 产物：CSV 作为 artifact 上传，便于人工复核。

**风险点**：CI 噪声导致随机失败 → 判据必须宽，且失败时给出「重跑一次」提示。

## 6. 上线监控与回滚预案

### 6.1 关键监控指标与阈值

方案 A 的全部指标（见 A §6.1）**全部保留**，追加：

| 指标 | 采集方式 | 告警阈值 | 说明 |
|---|---|---|---|
| **tick 处理耗时** | 周期性打点 | 超过基线 20% | T6 回归 |
| **定时尾部误差 max** | 周期性打点 | T7 开启时 > 0.5 ms | T7 有效性 |
| **IPC 最坏响应时延** | 打点 | > 基线 + 15.625 ms | T7 阻塞主线程的直接证据 |
| **按键漏发 / 重发** | 状态比对 | **> 0 即告警** | T6 的最严重失效模式 |
| CI bench 加速比 | CI 产物 | 低于历史值 50% | 收益回归 |

### 6.2 回滚触发条件

方案 A 的 4 条**全部保留**，追加：

5. **按键漏发或重发**（T6 引入）；
6. T7 开启后 IPC 最坏响应时延劣化超过一个网格；
7. CI bench 连续两次报加速比回归。

### 6.3 回滚步骤

回滚粒度按任务，**优先级从高到低**：

| 顺序 | 动作 | 成本 | 说明 |
|---|---|---|---|
| 1 | **关闭 T7 开关** | 极低（改配置，无需发版） | T7 任何异常都先走这一步 |
| 2 | `git revert` T7 提交 | 低 | 开关关闭仍有问题时 |
| 3 | `git revert` T6 提交 | 中 | 需复测四种模式 |
| 4 | `git revert` 其它单项 | 低 | 同方案 A |

> **T6 的回滚要特别小心**：它是本方案收益最大的一项（1.8~2.0×），
> 同时也是唯一改动热路径的一项。回滚后必须复测 tick 基准确认回到
> 31.7 / 84.6 µs 附近，**而不是更差**（排除回退不干净或换了个更慢的路径）。
