## 2. 方案 C 的三处前提需要修正

### 2.1 「四种调度模式」实为两套内核 + 一个配置别名

```ahk
; sender.ahk:277-288
static StartEnhancedPeriodic(...) {
    Sender.StartPeriodic(...)                                    ; ← 直接转调
    Sender._activeGroups[groupId]["mode"] := "enhanced_periodic"  ; ← 唯一差异
}
```

`state["mode"]` 在 `_ExecutePeriodic` / `_ExecuteSequence` 里**从未被读取**。
真正的差异只在配置解析侧（`executor.ahk:303-310`）：enhanced 用 `pressKeys`/`pressDelays`
字段名，基础版用 `keys`/`delays`。

**基准验证**（`bench_seqgen.ahk` C 阶段，2000 事件）：

```
alias,mode=periodic→enhanced_periodic,diffs=0,result=IDENTICAL
alias,mode=sequence→enhanced_sequence,diffs=0,result=IDENTICAL
```

**影响**：方案 C 的验收项写的是「periodic / sequence / enhanced_* **四种模式**的完整发送
时刻序列与旧实现一致」。四种里有两种是空转用例——应改为「两套内核 × 两种配置入口」，
把 enhanced 的验收落在**配置适配层**而不是调度层。

### 2.2 现网没有「序列生成」这一步

`_ExecutePeriodic`（`sender.ahk:442-532`）是**增量式调度**：每 tick 现算 target、
现算分桶、现推进基准。没有预生成、没有窗口、没有可回放的序列对象。

**影响**：T10「状态机化」的实际工作量比方案 C 描述的更大——不只是把状态搬进状态机，
还要**先把「生成」从定时器回调里剥出来**才谈得上状态机。`scheduling-design.md` 里的
`EventWindow` + 策略接口就是这一步的落地形态，已在原型中跑通（单测 53/53）。

### 2.3 术语映射

方案 C 沿用 JVM/多线程语境的表述（如「线程安全」）。AHK v2 是**单线程协作式**解释器，
对应约束是**重入安全 + 状态机不变量**（`scheduling-design.md` §5.3）。这不是文字问题：
真正的风险是定时器回调在 `Sleep` 让出点被重入，而不是数据竞争。

## 3. T10 · 定时器调度状态机化

### 3.1 原型实测（每 tick 耗时 p50，µs，三轮均值）

`NextDueUs`（求最早到期）+ `CollectInto`（分桶与推进）之和：

| 模式 | 键数 | 旧实现 | 新原型 | 加速比 |
|---|---|---|---|---|
| periodic | 8 | 21.4 | **13.7** | **1.56×** |
| periodic | 24 | 66.6 | **50.4** | **1.32×** |
| periodic | 64 | 177.8 | **143.3** | **1.24×** |
| sequence | 8 | 6.0 | **3.6** | **1.66×** |
| sequence | 24 | 6.0 | **3.6** | **1.68×** |
| sequence | 64 | 5.9 | **3.6** | **1.63×** |

（B 阶段 n=4221 与 F 阶段 n=8437 在 8 键下互相印证：21.43 vs 21.37 µs。）

### 3.2 口径警告：不能直接当作生产的 T10 达成证据

⚠️ **原型的「旧实现」只复刻了生产 4 次遍历中的 2 次**——
`NextDueUs` 对应「求 target」（`sender.ahk:462`），`Collect` 对应「分桶 + 推进」（`:481-506`）；
未复刻「补基准」（`:455-460`）与「算下次唤醒」（`:523`）两次。

因此：

- ✅ 可以证明：**架构方向可行**，且在遍历次数相同（新旧都是 2 次）的前提下，
  整数化 + 预夹紧 + 零分配仍带来 1.5~1.6×
- ❌ 不能证明：生产 T10 落地后就是 1.56× —— 真实的旧基线更慢（4 次遍历），
  真实收益可能更大；但也**不能简单与 T6 的 1.80~1.96× 相乘**，因为两者都削减了
  重复的 `_IntervalOf` 调用，**存在重叠**

**若要给 T10 一个可信的独立数字，需要把原型 old 补全成 4 次遍历再重测**——
这是建议的下一步（见 §7）。

### 3.3 对 M8 / M9 的判定

| 指标 | 基线 | T6 目标 | T10 目标 | 原型新实现 | 判定 |
|---|---|---|---|---|---|
| M8 · tick（8 键） | 31.7 µs | ≤ 20 µs | **≤ 15 µs** | **13.7 µs** | 达到 T10 目标值 |
| M9 · tick（24 键） | 84.6 µs | ≤ 50 µs | **≤ 35 µs** | **50.4 µs** | 仅达 T6，**未达 T10** |

⚠️ 由于 §3.2 的口径差异（原型 old 少了 2 次遍历，M8/M9 基线来自完整的
`bench_tick_traversal`），这两个判定**只作趋势参考，不作验收结论**。

### 3.4 新发现：键数越大，收益越小 —— 已用消融定位到排序（并推翻了初版建议）

加速比随键数下降：**1.56×（8 键）→ 1.32×（24 键）→ 1.24×（64 键）**。
初版把原因笼统归给「插入排序 O(m²)」但**没有量化**。补做 G 阶段消融
（`st.noSort` 开关，三轮 median）后得到确证：

| 键数 | sort=on | sort=off | 排序成本 | 占 collect | 加速(on) | 加速(off) |
|---|---|---|---|---|---|---|
| 8 | 8.4 µs | 7.0 µs | 1.4 µs | **17%** | 1.54× | **1.84×** |
| 24 | 37.7 µs | 23.9 µs | 13.8 µs | **37%** | 1.21× | **1.90×** |
| 64 | 111.4 µs | 65.5 µs | 45.9 µs | **41%** | 1.13× | **1.92×** |

**衰减 100% 由排序造成**：关掉排序后加速比恒为 ~1.9×，不再随键数变化。

> ⚠️ 初版 §3.4 的数字来自单轮（K=24 报「排序占 16%」），三轮 median 实为 **37%**。
> 排序成本对本轮同刻事件数极敏感，**单轮不可用于此类结论**。

#### 但初版给的两条建议都不成立

1. **「换成二路归并」—— 实测更慢。** 自底向上归并（暂存数组复用）与插入排序对拍，
   m=8 时慢 **4.19×**、m=13 慢 1.61×、m=38 慢 1.18×；要到 m=64 且**随机输入**才反超（0.58×），
   而生产的输入形态是「少量不同刻 + 大量同刻」的病态形态，恰好是归并最吃亏的一种。
   AHK 是解释器，归并的循环与临时数组搬运常数远大于插入排序的紧凑内层循环。
2. **「干脆不排序」—— 语义上不允许。** 同一 tick 内不同键的 `dueAt` 可以相差最多
   `WAKE_LEAD_MS`（28 ms），生产按 `dueAt` 分桶后**逐桶在其到期时刻精确发送**，
   因此 tick 内必须按到期时刻升序，不是「全部 Down → 等 → 全部 Up」一批了事。
   只有 **同一桶内**（dueAt 完全相同）的顺序才无关紧要。

#### 修正后的建议

**不优化排序**，理由有二：
- **量级上无关**：K=24 时排序 13.8 µs，一个定时器网格 15,625 µs，占比 0.09%；
- **无更优的比较排序**：见上。

真正值得记的是**排序成本的触发条件**——「大量键共用同一间隔 + 同一原点」时，
这些键的到期时刻永远相同、却排在少数不同刻的键之后，插入排序退化成 O(m²) 搬移。
若将来键数上到 K ≥ 64 且同刻事件常态化，正确方向是**按 distinct due 分桶**
（只排序 D 个不同的到期时刻，D ≪ m），而不是换比较排序算法。

## 4. T13 · `#Include` 收敛：收益上界远低于目标

### 4.1 生产依赖图实测

```
executor.ahk
  ├── ipc_client.ahk
  ├── hotkey_hook.ahk
  ├── sender.ahk
  │     ├── ipc_client.ahk      （重复，AHK #Include 每文件只包含一次，免费）
  │     └── high_res_clock.ahk
  └── joystick.ahk
```

**唯一被包含的文件数 = 5**（`ipc_client` / `hotkey_hook` / `sender` / `joystick` / `high_res_clock`），
共 6 条 `#Include` 语句。

### 4.2 `#Include` 边际成本复测

```
python tools/ahk-probes/bench_startup.py 7
...
#Include 边际成本:   825.11 us/文件        （本次复跑）
```

README 与 `plan-C-deep.md` 引用的是上一轮的 **673 µs/文件** —— **这个数本身在
673 ~ 825 µs/文件之间波动**，取区间更稳妥。

### 4.3 收益上界与目标的差距

| 项 | 值 |
|---|---|
| 可消除的 include 数（全部合并成 1 个文件，理论上限） | 5 |
| 收益上界 | 5 × 673 ~ 825 µs = **2.7 ~ 4.1 ms** |
| 现实收益（合并到 2~3 个文件） | **约 1.4 ~ 2.5 ms** |
| M11 目标 | **降 ≥ 15 ms** |
| 差距 | **约 4 ~ 6 倍** |

**结论：M11 的「降 ≥15 ms」在 T13 单独作用下不可能达成。**

原因不难理解：M11 的基线 164.33 ms（本次复跑 empty 基线 180.34 ms）**本身就是
一个空脚本的进程启动耗时**——AHK 解释器自身加载占大头，脚本侧的 `#Include`
只是零头。要省 15 ms，只能从**引擎加载/初始化**下手，那不是 T13 能碰的。

**建议**（三选一）：

1. 把 M11 目标改为「**降 ≥ 3 ms**」，T13 保留为 P2 收尾项；
2. 或把 T13 从「性能优化」重新定性为「**依赖图治理**」——收益是图谱更清晰、
   跨层依赖更容易被发现（配合 `.review-analysis/build_graph.py`），性能只是顺带；
3. 或**直接取消 T13**，把精力放到真正有大头的 T6/T10。

> 本项目的一条经验是「不要把负面结论藏起来」（README §2 规则 2）。
> T13 属于**量级判断失误**，早修正比做到一半再发现便宜得多。

## 5. T9 · 序列化流式输出：仍属未实测，附可执行协议

本次**没有**为 T9 产出双实现基准（工作量大且与调度主线无关）。为避免它继续停留在
「结构性理由」，这里把协议写死，任何人接手即可执行：

| 项 | 内容 |
|---|---|
| 现有基线 | M1 = 1.29 ms（2 KB p50）、M2 = 5.44 ms（8 KB p50），来源 `bench_json_escape` |
| T1 后目标 | M1 ≤ 0.10 ms、M2 ≤ 0.30 ms |
| **T9 后目标** | M1 ≤ 0.05 ms、M2 ≤ 0.15 ms |
| 新增基准 | `bench_json_full`：两个实现 —— 现有递归 `result .= ...` vs 预分配 `Buffer` + 索引写入 |
| 等价性 | **逐字节相同**；覆盖空对象 / 空数组 / 单元素 / 超长键名 / 深度 255 / 混合类型 |
| **一票否决项** | **峰值内存不得高于旧实现**（流式若靠反复扩容，内存会更差） |
| 判定门槛 | 收益不达标则该任务**直接降级或取消**（沿用方案 C 的 M1 阶段定义） |

⚠️ 特别提醒：`json_serializer.ahk:62` 的 `result .= nextSpaces ...` 是 O(n²) 的来源，
但「改成流式」在 AHK 里有个陷阱——**字符串拼接在 AHK 里有写时复制优化，
换成 Buffer 未必更快**，必须实测。这正是 T9 不能靠推理定案的原因。

## 6. A/B/C 裁决更新

| 维度 | A · 保守 | **B · 平衡（仍推荐）** | C · 深度 |
|---|---|---|---|
| 最高单项收益 | 序列化降 94.7~97.6% | A + tick **1.80~1.96×** | B + **架构可测性**（真实收益待 T10 补全基线） |
| 未实测项 | 无 | 无 | **T9 仍未实测；T13 目标证伪** |
| 启动收益 | — | — | **M11「≥15 ms」证伪**，上界 2.7~4.1 ms |
| 最严重失效模式 | 输出不一致 | 按键漏发/重发 | **调度卡死** |

**裁决不变：仍推荐 B。**

变化的是 C 的定位：

- C 的**价值从「性能」转移到「可测性与正确性」**——本次最硬的收益不是 1.56×，
  而是**浮点拆桶率 94% → 0%**（`scheduling-bench` §6）。那是真实的行为缺陷，
  不是性能数字。
- C 的**风险排序不变**（T10 回滚成本最高），但 T13 的风险收益比明显变差，
  建议从 C 的清单里挪出去或降级。

## 7. 建议的下一步（按性价比排序）
