## 2. 方案 C 的三处前提需要修正

### 2.1 「四种调度模式」实为两套内核 + 一个配置别名

```ahk
; sender.ahk:277-288
static StartEnhancedPeriodic(...) {
    Sender.StartPeriodic(...)                                    ; ← 直接转调
    Sender._activeGroups[groupId]["mode"] := "enhanced_periodic"  ; ← 唯一差异
}
```

`state["mode"]` 在 `_ExecutePeriodic` / `_ExecuteSequence` 里**从未被读取**。
真正的差异只在配置解析侧（`executor.ahk:303-310`）：enhanced 用 `pressKeys`/`pressDelays`
字段名，基础版用 `keys`/`delays`。

**基准验证**（`bench_seqgen.ahk` C 阶段，2000 事件）：

```
alias,mode=periodic→enhanced_periodic,diffs=0,result=IDENTICAL
alias,mode=sequence→enhanced_sequence,diffs=0,result=IDENTICAL
```

**影响**：方案 C 的验收项写的是「periodic / sequence / enhanced_* **四种模式**的完整发送
时刻序列与旧实现一致」。四种里有两种是空转用例——应改为「两套内核 × 两种配置入口」，
把 enhanced 的验收落在**配置适配层**而不是调度层。

### 2.2 现网没有「序列生成」这一步

`_ExecutePeriodic`（`sender.ahk:442-532`）是**增量式调度**：每 tick 现算 target、
现算分桶、现推进基准。没有预生成、没有窗口、没有可回放的序列对象。

**影响**：T10「状态机化」的实际工作量比方案 C 描述的更大——不只是把状态搬进状态机，
还要**先把「生成」从定时器回调里剥出来**才谈得上状态机。`scheduling-design.md` 里的
`EventWindow` + 策略接口就是这一步的落地形态，已在原型中跑通（单测 53/53）。

### 2.3 术语映射

方案 C 沿用 JVM/多线程语境的表述（如「线程安全」）。AHK v2 是**单线程协作式**解释器，
对应约束是**重入安全 + 状态机不变量**（`scheduling-design.md` §5.3）。这不是文字问题：
真正的风险是定时器回调在 `Sleep` 让出点被重入，而不是数据竞争。

## 3. T10 · 定时器调度状态机化

### 3.1 原型实测（每 tick 耗时 p50，µs，三轮均值）

`NextDueUs`（求最早到期）+ `CollectInto`（分桶与推进）之和：

| 模式 | 键数 | 旧实现 | 新原型 | 加速比 |
|---|---|---|---|---|
| periodic | 8 | 21.4 | **13.7** | **1.56×** |
| periodic | 24 | 66.6 | **50.4** | **1.32×** |
| periodic | 64 | 177.8 | **143.3** | **1.24×** |
| sequence | 8 | 6.0 | **3.6** | **1.66×** |
| sequence | 24 | 6.0 | **3.6** | **1.68×** |
| sequence | 64 | 5.9 | **3.6** | **1.63×** |

（B 阶段 n=4221 与 F 阶段 n=8437 在 8 键下互相印证：21.43 vs 21.37 µs。）

### 3.2 口径警告：不能直接当作生产的 T10 达成证据

~~⚠️ 原型的「旧实现」只复刻了生产 4 次遍历中的 2 次~~ —— **已于 2026-09-14 补全并消除。**

#### 3.2b 口径已修正：原型 old 补齐到 4 次遍历后的重测

给 `LegacyPeriodicPolicy` 补上原先缺的两次遍历，并把新的 `PeriodicPolicy` 的
「第 4 次遍历」融进「第 3 次遍历」（推进基准时顺手维护 running min）：

| 遍历 | 生产位置 | 旧实现 | 新实现 |
|---|---|---|---|
| T1 补基准 | `sender.ahk:449-452` | 每 tick n 次 `Map.Has` | **0**（`Init` 预置 bases） |
| T2 求最小到期 | `:457-461` | O(K) 扫描 | O(K) `NextDueUs` |
| T3 收集 + 推进 | `:476-510` | O(K) + Map 分桶 | O(K) `CollectInto` |
| T4 算下次唤醒 | `:518-522` | **又一次完整 O(K) 扫描** | **O(1)**（读 T3 维护的 `minNextUs`） |

三轮 median，p50 µs：

| 键数 | 旧 T1+T2+T3+T4 | 新 T1+T2+T3+T4 | 加速比 | （旧口径：只算 T2+T3） |
|---|---|---|---|---|
| 8 | 3.2 + 8.4 + 12.9 + 8.4 = **32.8** | 0.8 + 5.2 + 9.2 + 1.0 = **16.2** | **2.02×** | 1.48× |
| 24 | 7.2 + 21.2 + 45.3 + 21.0 = **94.3** | 0.8 + 12.4 + 41.0 + 1.1 = **55.2** | **1.71×** | 1.25× |
| 64 | 17.1 + 53.2 + 125.5 + 52.5 = **248.1** | 0.8 + 30.5 + 121.0 + 1.1 = **153.4** | **1.62×** | 1.18× |

**两个交叉验证（口径警告由此消除）**：

1. 原型 old @ K=8 = **32.8 µs**，与 `bench_tick_traversal` 独立测到的 M8 基线
   **31.7 µs** 只差 3% → 两套基准的「旧实现」现在同口径。
2. 修正后的加速比 **2.02×**（K=8）落在 T6 独立测到的 **1.80~1.96×** 区间上沿 →
   不再需要「不可相乘」的保留意见。

**最值钱的发现**：T4（`sender.ahk:518-522` 算下次唤醒）在旧实现里是**一整次 O(K) 全扫描**
（8.4 / 21.0 / 52.5 µs，几乎等于 T2 的成本），因为它在发送完成后按推进过的基准重算
最小剩余时间。新实现把它融进 T3 的推进循环，退化成 O(1) —— 这一项就贡献了
总收益的约 **40%**。

### 3.3 对 M8 / M9 的判定（已按 4 次遍历口径修正）

| 指标 | 基线 | T6 目标 | T10 目标 | 原型新实现 | 判定 |
|---|---|---|---|---|---|
| M8 · tick（8 键） | 31.7 µs | ≤ 20 µs | **≤ 15 µs** | **16.2 µs** | 达 T6，**未达 T10（差 8%）** |
| M9 · tick（24 键） | 84.6 µs | ≤ 50 µs | **≤ 35 µs** | **55.2 µs** | **未达 T6，更未达 T10** |

> ⚠️ **判定比初版更严，不是更好**：初版 M8 报「13.7 µs 达成 T10」，那是**只算 T2+T3** 的结果；
> 补上 T1/T4 后是 16.2 µs，反而**够不到 15 µs 的 T10 目标**。M9 也从 50.4 涨到 55.2，
> 连 T6 的 ≤50 µs 都差一截。
>
> 但结论反而**更可信**：现在与 `bench_tick_traversal` 的基线（31.7 / 84.6，本身就是
> 4 次遍历口径）可以直接对比，不再有口径折扣。

### 3.4 新发现：键数越大，收益越小 —— 已用消融定位到排序（并推翻了初版建议）

加速比随键数下降：**1.56×（8 键）→ 1.32×（24 键）→ 1.24×（64 键）**。
初版把原因笼统归给「插入排序 O(m²)」但**没有量化**。补做 G 阶段消融
（`st.noSort` 开关，三轮 median）后得到确证：

| 键数 | sort=on | sort=off | 排序成本 | 占 collect | 加速(on) | 加速(off) |
|---|---|---|---|---|---|---|
| 8 | 8.4 µs | 7.0 µs | 1.4 µs | **17%** | 1.54× | **1.84×** |
| 24 | 37.7 µs | 23.9 µs | 13.8 µs | **37%** | 1.21× | **1.90×** |
| 64 | 111.4 µs | 65.5 µs | 45.9 µs | **41%** | 1.13× | **1.92×** |

**衰减 100% 由排序造成**：关掉排序后加速比恒为 ~1.9×，不再随键数变化。

> ⚠️ 初版 §3.4 的数字来自单轮（K=24 报「排序占 16%」），三轮 median 实为 **37%**。
> 排序成本对本轮同刻事件数极敏感，**单轮不可用于此类结论**。

#### 但初版给的两条建议都不成立

1. **「换成二路归并」—— 实测更慢。** 自底向上归并（暂存数组复用）与插入排序对拍，
   m=8 时慢 **4.19×**、m=13 慢 1.61×、m=38 慢 1.18×；要到 m=64 且**随机输入**才反超（0.58×），
   而生产的输入形态是「少量不同刻 + 大量同刻」的病态形态，恰好是归并最吃亏的一种。
   AHK 是解释器，归并的循环与临时数组搬运常数远大于插入排序的紧凑内层循环。
2. **「干脆不排序」—— 语义上不允许。** 同一 tick 内不同键的 `dueAt` 可以相差最多
   `WAKE_LEAD_MS`（28 ms），生产按 `dueAt` 分桶后**逐桶在其到期时刻精确发送**，
   因此 tick 内必须按到期时刻升序，不是「全部 Down → 等 → 全部 Up」一批了事。
   只有 **同一桶内**（dueAt 完全相同）的顺序才无关紧要。

#### 修正后的建议

**不优化排序**，理由有二：
- **量级上无关**：K=24 时排序 13.8 µs，一个定时器网格 15,625 µs，占比 0.09%；
- **无更优的比较排序**：见上。

真正值得记的是**排序成本的触发条件**——「大量键共用同一间隔 + 同一原点」时，
这些键的到期时刻永远相同、却排在少数不同刻的键之后，插入排序退化成 O(m²) 搬移。
若将来键数上到 K ≥ 64 且同刻事件常态化，正确方向是**按 distinct due 分桶**
（只排序 D 个不同的到期时刻，D ≪ m），而不是换比较排序算法。

## 4. T13 · `#Include` 收敛：收益上界远低于目标

```
executor.ahk
  ├── ipc_client.ahk
  ├── hotkey_hook.ahk
  ├── sender.ahk
  │     ├── ipc_client.ahk      （重复，AHK #Include 每文件只包含一次，免费）
  │     └── high_res_clock.ahk

```

**唯一被包含的文件数 = 5**（`ipc_client` / `hotkey_hook` / `sender` / `joystick` / `high_res_clock`），
共 6 条 `#Include` 语句。

### 4.2 `#Include` 边际成本复测

```
python tools/ahk-probes/bench_startup.py 7
...
#Include 边际成本:   825.11 us/文件        （本次复跑）
```

README 与 `plan-C-deep.md` 引用的是上一轮的 **673 µs/文件** —— **这个数本身在
673 ~ 825 µs/文件之间波动**，取区间更稳妥。

### 4.3 收益上界与目标的差距

| 项 | 值 |
|---|---|
| 可消除的 include 数（全部合并成 1 个文件，理论上限） | 5 |
| 收益上界 | 5 × 673 ~ 825 µs = **2.7 ~ 4.1 ms** |
| 现实收益（合并到 2~3 个文件） | **约 1.4 ~ 2.5 ms** |
| M11 目标 | **降 ≥ 15 ms** |
| 差距 | **约 4 ~ 6 倍** |

**结论：M11 的「降 ≥15 ms」在 T13 单独作用下不可能达成。**

原因不难理解：M11 的基线 164.33 ms（本次复跑 empty 基线 180.34 ms）**本身就是
一个空脚本的进程启动耗时**——AHK 解释器自身加载占大头，脚本侧的 `#Include`
只是零头。要省 15 ms，只能从**引擎加载/初始化**下手，那不是 T13 能碰的。

**建议**（三选一）：

1. 把 M11 目标改为「**降 ≥ 3 ms**」，T13 保留为 P2 收尾项；
2. 或把 T13 从「性能优化」重新定性为「**依赖图治理**」——收益是图谱更清晰、
   跨层依赖更容易被发现（配合 `.review-analysis/build_graph.py`），性能只是顺带；
3. 或**直接取消 T13**，把精力放到真正有大头的 T6/T10。

> 本项目的一条经验是「不要把负面结论藏起来」（README §2 规则 2）。
> T13 属于**量级判断失误**，早修正比做到一半再发现便宜得多。

## 5. T9 · 序列化流式输出：**前提证伪，建议取消**（2026-09-14 已立基准）

### 5.1 基准设计

`tools/ahk-bench/bench_json_full.ahk`：五个实现**共用同一套缩进/分派/转义规则，只换累加方式**。

| 实现 | 做法 |
|---|---|
| `concat` | 原样复刻 `json_serializer.ahk`（递归返回 + `result .= ...`） |
| `parts` | 递归收集进数组，最后一次拼接 |
| `buf` | 预分配 `Buffer` + `StrPut` 索引写入，容量倍增 |
| `stream` | **单一 ByRef 累加器**，递归不返回字符串（规范流式写法，零中间字符串） |
| `streamp` | `stream` + `VarSetStrCapacity` 预分配容量 |

转义单独参数化：`esc=old`（生产现状，对照 1.29 / 5.44 ms 基线）与 `esc=new`（T1 落地后的水平）。
每实现预热 20 次；2 KB 取 300 样本、8 KB 取 150 样本；三轮取中位数。

**等价性**：8 个边界用例（空 Map / 空 Array / 单元素 / 300 字符超长键名 / 深度 60 /
混合类型含 CJK 与转义字符）下五种实现的输出**逐字节相同**（`equiv,summary,ok=8,bad=0`）。

### 5.2 实测（p50，ms，三轮中位数）

规模 2 KB（实际 2056 字符 / 11 条）、8 KB（实际 8428 字符 / 47 条）：

| 实现 | esc | 2 KB p50 | 三轮区间 | 8 KB p50 | 三轮区间 | vs concat |
|---|---|---|---|---|---|---|
| `concat` | old | **0.8776** | 0.8614 – 0.9197 | **3.5606** | 3.4083 – 3.5885 | 基线（生产现状） |
| `concat` | new | **0.4995** | 0.4867 – 0.5546 | **2.0600** | 2.0406 – 2.1244 | — |
| `stream` | new | 0.4979 | 0.4647 – 0.5069 | 2.0382 | 1.9327 – 2.1321 | 区间重叠，**未测出差异** |
| `streamp` | new | 0.4855 | 0.4779 – 0.5184 | 2.0160 | 1.9944 – 2.0659 | 区间重叠，**未测出差异** |
| `parts` | new | 0.5643 | 0.5514 – 0.5895 | 2.3338 | 2.2263 – 2.3515 | **显著慢 13.0% / 13.3%** |
| `buf` | new | 0.7292 | 0.7234 – 0.7509 | 3.0280 | 2.8864 – 3.0423 | **显著慢 46.0% / 47.0%** |

判定口径沿用统计纪律：区间重叠即「未测出差异」；`parts` / `buf` 与 `concat` 区间**不重叠**，
故「更慢」是实打实的。

### 5.3 前提证伪：`result .=` 根本不是 O(n²)

三条独立证据：

1. **缩放是严格线性的**。字符数 2056 → 8428（4.10×），`concat/new` 耗时 0.4995 → 2.0600（**4.12×**）。
   O(n²) 在这里会表现为约 16.8×，实测 4.12× —— 线性项完全主导。
2. **`stream` 相对 `concat` 没有收益**。`stream` 消除了所有中间字符串返回，
   若二次拷贝真的存在，它应当显著更快；实测两者三轮区间完全重叠。
3. **合成拼接探针**（`result .=` vs 数组+join vs Buffer，100 / 400 / 1600 / 6400 段）：
   18.7 / 65.1 / 439.3 / 1897.4 µs，段数 64× 而耗时 101× —— `result .=` 全程最快且近线性。

**反直觉的部分**：两种「更激进」的流式实现反而更慢。`buf` 慢 46%（每次 `BufPut` 都要
`StrLen` + 边界检查 + `StrPut` 的 DllCall 级开销），`parts` 慢 13%（数组持有全部片段，
最后一次拼接把所有片段又走了一遍）。

### 5.4 目标差距（一票否决：不达标即取消）

| 目标 | 门槛 | 实测最佳 | 差距 |
|---|---|---|---|
| **T9** M1（2 KB p50） | ≤ 0.05 ms | 0.4855 ms | **超 9.7×** |
| **T9** M2（8 KB p50） | ≤ 0.15 ms | 2.0160 ms | **超 13.4×** |
| T1 M1 | ≤ 0.10 ms | 0.4995 ms | 超 5.0× |
| T1 M2 | ≤ 0.30 ms | 2.0600 ms | 超 6.9× |

### 5.5 成本构成：改累加方式救不了，瓶颈在别处

`esc=old → new` 的差就是转义成本：2 KB 占 **43.1%**（0.3781 / 0.8776）、8 KB 占 **42.1%**。
也就是说**即使转义完全免费**，仍剩 0.50 / 2.06 ms，距 M1 目标仍有 10 倍。
按字符摊：`0.4995 ms / 2056 字符 = 0.243 µs/字符 ≈ 243 ns/字符` —— 这是 AHK 解释器的
「Map 遍历 + 拼接」每字符固定成本，**与拷贝量级无关**。

**一票否决项（内存）**：三轮 `priv_delta_kb` 绝大多数为 0 或 ±几十 KB；
仅 `parts` 在 8 KB 出现一轮 +228 KB（数组同时持有全部片段）。
没有实现表现出内存优势，也没有强证据触发否决 —— 否决 T9 靠的是**收益**，不是内存。

### 5.6 判定与连带结论

> **T9 建议取消。** 前提（O(n²) 二次拷贝）已被证伪；三种流式实现无一显著更快、
> 两种显著更慢；目标差 1~2 个数量级，且成本构成显示瓶颈在解释器每字符开销。

**连带结论：T1 的目标同样不可达。** T1 实测收益稳定在 **1.73× ~ 1.76×**（2 KB 1.76×、8 KB 1.73×），
而它的目标要求从 1.29 ms 降到 0.10 ms（12.9×）。T1 仍**值得做**（白拿 43%），
但目标值必须改。

**真正的出路不是优化序列化，而是少序列化**：0.24 µs/字符 的常数决定了任何
「改实现」的路线都到不了 0.05 ms。可行方向只有缓存序列化结果（配置不变时复用）、
或改为增量/按需序列化。这属于设计层改动，不在方案 C 的范围内。

### 5.7 执行时踩到的两个 AHK 硬坑（写在这里免得再踩）

1. **不接受单行花括号函数体**：`F(x) { return x * 2 }` 报 `Unexpected {`，必须写成多行。
2. **标识符大小写不敏感**：若函数名叫 `Spaces`，而调用方有局部变量 `spaces`，
   则 `Spaces(cur)` 会被解析成那个尚未赋值的局部变量，报
   `This local variable has not been assigned a value`。
   生产代码用 `this._BuildSpaces`（方法调用）天然躲开；基准里已把函数改名为 `BuildSpaces`、
   局部变量改为 `pad` / `nextPad`。

## 6. A/B/C 裁决更新

| 维度 | A · 保守 | **B · 平衡（仍推荐）** | C · 深度 |
|---|---|---|---|
| 最高单项收益 | 序列化降 94.7~97.6% | A + tick **1.80~1.96×** | B + **架构可测性**（真实收益待 T10 补全基线） |
| 未实测项 | 无 | 无 | **无**（T9 / T10 / T13 均已实测；T9、T13 已证伪） |
| 启动收益 | — | — | **M11「≥15 ms」证伪**，上界 2.7~4.1 ms |
| 最严重失效模式 | 输出不一致 | 按键漏发/重发 | **调度卡死** |

**裁决不变：仍推荐 B。**

变化的是 C 的定位：

- C 的**价值从「性能」转移到「可测性与正确性」**——本次最硬的收益不是 2.02×，
  而是**浮点拆桶率 94% → 0%**（`scheduling-bench` §6）。那是真实的行为缺陷，
  不是性能数字。
- C 的**风险排序不变**（T10 回滚成本最高）。T13（目标证伪）与 T9（前提证伪）
  均建议从 C 的清单里挪出去或取消：**C 现在值得做的只剩 T6 与「时刻表示用 int µs」**。
