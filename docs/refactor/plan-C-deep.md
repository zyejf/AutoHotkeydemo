## 0. 方案定位

**一句话**：在方案 B 之上做**架构级**改造 —— 重写序列化层、把定时器调度状态机化、
统一观测埋点、收敛启动依赖图。

| 维度 | 说明 |
|---|---|
| 改动面 | 12+ 文件、跨 3 个分层；涉及模块边界与数据结构 |
| 是否需要开关 | **是**（T9、T10 各需独立开关；T12 需采样开关） |
| 预期周期 | 最长（需要架构评审 + 图谱复核 + 更长灰度） |
| 适用场景 | 有专门的迭代窗口；已用方案 B 拿到确定收益后仍有性能/稳定性诉求；团队能承受架构演进 |

**⚠️ 本方案三分之一的任务「收益未实测」。** 与 A/B 不同（A/B 的每一项都有本机实测数字），
C 的 T9 / T10 / T13 目前只有**结构性理由**和**间接实测线索**，没有直接的双实现基准。
因此本方案对这些任务设了一条硬规则：**先立基准，再实施**（见 §3 各任务的「前置条件」）。

### 1.2 三条实测线索（构成本方案立项依据）

1. **`#Include` 边际成本 673 µs/文件**（实测 `inc_1000_x50` 相对 `empty` 增 35.19 ms / 50 文件）。
   而脚本**行数**本身很便宜（解析 1.44 µs/行）。
   → **减少 `#Include` 数量**是启动优化里唯一有确定量级的杠杆（T13）。
2. **字符串拼接仍是序列化层的结构性瓶颈**。T1 只修掉了 `_EscapeString` 一处 O(n²)，
   但 `_StringifyObject` / `_StringifyArray` 仍在用 `result .=` 累积
   （`json_serializer.ahk:62` 可见 `result .= nextSpaces ...`）。→ T9。
3. **定时器调度的复杂度是结构性的**：`_ExecutePeriodic` / `_ExecuteSequence` /
   `_ExecuteEnhanced*` 多条路径各自维护「基准时刻 / 到期判断 / 重排」，
   同一份按键表被遍历 4 次（T6 已合并，但状态仍分散在多个 Map 里）。→ T10。

## 3. 实施方案与风险评估

> T1~T8 的实现路径与风险**同方案 A / B**。以下只写 C 的增量任务。

### T9 · 序列化层改为缓冲流式输出（P1，收益未实测）

**现状与线索**：`_StringifyValue` / `_StringifyObject` / `_StringifyArray`
全程用 `result .=` 累积字符串（`json_serializer.ahk:62` 可见典型形态）。
每次 `.=` 都可能触发重新分配 + 整串拷贝，与 T1 修掉的 `_EscapeString` 是同一类问题，
只是分散在更多地方、单次增量更小。

**前置条件（硬）**：必须先写 `bench_json_full.ahk` —— 内置新旧两套完整序列化实现，
对真实配置对象与深嵌套结构做**逐字节等价性 + 耗时**对比。
**基准未产出前不得动生产代码。**

**实现路径**：

1. 用一个 `Array` 作为输出缓冲，所有片段 `Push` 进去。
2. 结束时一次性 `Join`（或分段 Join 以控制峰值内存）。
3. 缩进与换行同样走缓冲，不再拼到结果串上。
4. 保留 `_StringifyValue` 的 `visited` 环检测 —— **这个不能丢**。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 输出与旧实现不一致 | 配置损坏 / IPC 解析失败 | 逐字节等价性用例（必须覆盖所有既有用例的输入） |
| **峰值内存反而上升** | 缓冲数组 + 最终串同时存在 | 基准必须同时测**耗时与峰值内存**，内存若上升即否决 |
| 改动面过大 | 整个文件重写，review 困难 | 分两个提交：先加缓冲（旧路径并存），再切流 |

**兼容性影响**：对外接口不变。需开关（`jsonStreamMode`，默认关）。

---

### T10 · 定时器调度状态机化（P2，收益未实测）

**现状与线索**：periodic / sequence / enhanced_periodic / enhanced_sequence
四条路径各自维护「基准时刻 / 到期判断 / 重排」，状态分散在
`_activeGroups` 的多个子 Map 里（`triggerTimes` / `intervals` / `delays` / `step` …）。
T6 合并了遍历，但**状态本身仍然分散**，导致任何一处状态推进都要跨多个 Map 同步。

**前置条件（硬）**：先写 `bench_scheduler.ahk`，覆盖四种模式 × 三种规模，
输出「发送时机序列」作为等价性比对依据。**基准未产出前不得动生产代码。**

**实现路径**：

1. 定义显式的调度状态：`IDLE → ARMED → FIRING → RELEASING → (回到 ARMED)`。
2. 每个分组持有一个状态对象，包含全部调度所需字段（不再跨 Map 取）。
3. 四条路径只保留「如何计算下一次触发时刻」的差异，其余共用状态机。
4. 状态迁移处统一埋点（配合 T12）。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| **这是本方案风险最高的一项** | 等价于重写定时核心 | 必须带开关；灰度期独立于其它改动放量 |
| 节拍漂移 | 状态迁移顺序变化导致相位偏移 | 等价性基准比对**完整发送时刻序列**，不是抽样 |
| 与既有 `droppedTriggers` 语义冲突 | 保相位逻辑被改动 | 明确保相位规则（用「本次计划时刻」推进，滞后不重置基准） |

**兼容性影响**：对外无影响（同 B 的 T6）。需开关（`schedulerV2`，默认关）。

---

### T13 · 启动：`#Include` 收敛（P2，有实测线索）

**线索**：`#Include` 边际成本 **673 µs/文件**，而解析仅 1.44 µs/行。
因此**文件数量**才是启动成本的主导项，不是行数。

**前置条件**：先用 `build_graph.py` 导出当前 `#Include` 图，
统计主脚本的可达文件数与层级深度，确认「收敛 N 个文件 ≈ 省 N × 0.67 ms」。

**实现路径**：

1. 合并语义内聚的小模块（同一层的强内聚类合并为一个文件）。
2. 消除**重复包含**与**无谓的间接包含**（A include B 只为拿到 B 里的一个工具函数）。
3. ⚠️ **不得为了减少文件数而破坏分层**：合并只在同层内进行，
   跨层合并会引入逆向边，直接违反闸门①与 `AGENTS.md` 的分层规则。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 合并引入跨层依赖 | 产生逆向边 / 环 | 每次合并后重跑图谱；新增环即回滚该次合并 |
| 合并后文件过大 | 可读性下降 | 设定单文件上限（建议 ≤ 800 行） |
| 收益不及预期 | 673 µs 是夹具文件的成本，真实文件更大 | 先做小批量试点（合并 3~5 个文件）验证斜率 |

---

### T12 · 统一观测埋点（P1）

**动机**：A/B 方案的监控指标（§6.1）目前只能靠「日志 ERROR 计数 + 用户反馈」间接观测。
方案 C 既然要动架构，就应该同时把可观测性补齐 —— 否则更大幅度的改动将无从判断。

**实现路径**：

1. 定义统一的埋点结构：`{ts, level, component, event, duration_us, …}`。
2. 在关键路径埋点：序列化耗时、tick 耗时、发送时机误差、状态迁移。
3. 采样开关（默认低频采样，避免埋点本身成为性能负担）。
4. 输出复用 `error_system.ahk` 的落盘与轮转能力（**不新建第二套日志设施**）。

**风险点**：埋点自身开销 → 必须采样且可关闭；埋点字段变更影响下游 → 结构需版本化。

## 6. 上线监控与回滚预案

### 6.1 关键监控指标与阈值

### 6.2 回滚触发条件

8. 序列化输出与旧实现不一致（**立即关闭 T9 开关**）；
9. 调度状态机出现非预期状态或卡死（**立即关闭 T10 开关**）；
10. 启动耗时高于基线 + 5%（回滚 T13 的合并）；
11. 图谱复核发现新增环或跨层违规（**无条件回滚**该项合并）。

### 6.3 回滚步骤

回滚粒度按任务，**成本从低到高**：

| 顺序 | 动作 | 成本 | 说明 |
|---|---|---|---|
| 1 | **关闭对应开关**（T9 / T10 / T7） | 极低 | 架构项任何异常都先走这一步 |
| 2 | 关闭 T12 采样 | 极低 | 埋点异常时的第一动作 |
| 3 | `git revert` T10 提交 | **高** | 定时核心重写，回滚后必须复测四种模式的完整发送序列 |
| 4 | `git revert` T9 提交 | 中 | 回滚后复测序列化耗时与峰值内存 |
| 5 | `git revert` T13 的合并提交 | 中 | 回滚后重跑图谱与启动基准 |
| 6 | `git revert` T6 及其他单项 | 低~中 | 同方案 B |

> **T10 是回滚成本最高的一项**，也是唯一「回滚后仍需长时间压测才能确认恢复」的项。
> 这正是它被定为 P2、且必须单独灰度的原因。

### 6.4 应急联系人机制

同方案 A §6.4，追加两条：

- **架构评审人**：T9 / T10 / T13 的回滚决策需架构评审人参与
  （判断「关开关」是否足够，还是必须 revert）；
- **图谱负责人**：任何涉及 `#Include` 与分层的回滚，需重跑图谱并确认无新增环。

> 上表为**角色定义**，kick-off 时必须填入具体人名与值班表；
> 无人认领的角色视为该方案不具备上线条件。
