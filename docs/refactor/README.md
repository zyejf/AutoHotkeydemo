# AHK 脚本重构 · 方案索引与选型指南

> 本目录回答一个问题：**在不改变既有行为的前提下，AHK 侧该怎么重构、能拿到多少收益、风险有多大。**
>
> 所有收益数字都来自 `tools/ahk-bench/` 的**新旧双实现基准**，不是估算。
> **生产代码一行未改。**

## 2. 选型决策树

```
能否接受改动定时器主循环（sender.ahk 的 _Execute*）？
├─ 否 ────────────────────────────► 方案 A
│
└─ 是
   ├─ 是否有专门的迭代窗口 + 能做架构评审？
   │  ├─ 否 ──────────────────────► 方案 B
   │  └─ 是
   │     ├─ 是否已用 B 拿到收益、且仍有性能/稳定性诉求？
   │     │  ├─ 是 ────────────────► 方案 C
   │     │  └─ 否 ────────────────► 先做 B，C 作为后续
   │     └─ 是否接受「部分任务收益未实测」？
   │        ├─ 接受 ───────────────► 方案 C（T9 / T10 / T13 均有评测；T9 与 T13 已证伪）
   │        └─ 不接受 ─────────────► 方案 B
```

**三条经验规则：**

1. **不确定就选 B。** A 拿不到 tick 路径的 1.8~2.0×，C 的三分之一任务收益未实测；
   B 的每一项都有本机实测数字支撑。
2. **不要为了「看起来优化了」去改 T（键名校验）。** 实测只有 1.03×，
   三份计划的任务清单里**都不含这一项** —— 这是刻意保留的负面结论。
3. **T7（定时器策略）永远最后做、且带开关。** 它的收益只是「消除尾部抖动」，
   不是「提升精度」，CPU 影响也不可复现 —— 最容易被误读成收益的一项。

## 3. 判定指标统一定义

三份计划共用同一套编号，避免跨方案对齐时混淆。

| 编号 | 指标 | 基线 | 测量方式 |
|---|---|---|---|
| M1 | JSON 序列化耗时（2 KB）p50 | 1.29 ms | `bench_json_escape` |
| M2 | 大字符串序列化（8 KB）p50 | 5.44 ms | 同上 |
| M3 | 异常守卫覆盖率 | 0/3 | `bench_stability` |
| M4 | 长跑内存残留（5 万次） | 19.5 MB | `bench_cycle_leak` |
| M5 | CPU 占用率（8 组 × 100 ms） | 20.7 ~ 25.0%（多轮） | `bench_timer_storm` |
| M6 | 启动时间（外部墙钟） | 164.33 ms（n=11） | `tools/ahk-probes/bench_startup.py` |
| M7 | 回归基线 | 642 / 642 | `scripts/check-gates.sh` |
| M8 | tick 处理（8 键）p50 | 31.7 µs | `bench_tick_traversal` |
| M9 | tick 处理（24 键）p50 | 84.6 µs | 同上 |
| M10 | 定时尾部误差 max | 1.05 ~ 4.92 ms（跨轮摆动） | `bench_timer_storm` |
| M11 | 启动时间降幅 | — | 仅 C 的 T13 |
| M12 | 架构健康度（环 / 逆向边） | 0 环 / 3 违规（白名单） | `.review-analysis/build_graph.py` |

### 统计口径（四份文档通用，不得违反）

1. **用 p50 判定，不用 max。** `误差 max` 只是一个最坏样本；
   实测同一变体在多轮间可从 1.05 ms 变到 4.92 ms。
2. **P95 只在样本量足够时用。** `_Pct(arr,0.95)` 的索引是 `Ceil(n*0.95)`，
   n=54 时只容忍 2 个离群点；离群幅度（约 15 ms 一个调度网格）远大于阈值时 P95 会随机变红。
   **判断漂移用中位数。**
3. **结论必须跨轮可复现。** 单轮结论一律不作为验收依据。
4. **CPU 类结论必须给出多轮区间并检查重叠。** 重叠即视为「未测出差异」，不得写入收益。

### 启动时间（M6）的特殊说明

进程创建本身就占绝大部分：本机 `hostname.exe` 基线 **144.85 ms**（Defender 扫描），
AHK 空脚本 **164.33 ms** → **引擎自身仅约 19 ms**。
**必须先测 `hostname.exe` 再测 AHK**，否则会把 Defender 的波动误判成引擎回归。

## 4. Demo：如何复现全部实测数据

### 4.1 跑基准

```bash
# 单个
bash tools/ahk-bench/run.sh json_escape

# 全部（cycle_leak 除外，它必须每用例独立进程）
for id in json_escape tick_traversal key_regex timer_storm stability; do \
    bash tools/ahk-bench/run.sh $id; \
done
bash tools/ahk-bench/cycle_leak_all.sh
```

CSV 输出到 `%TEMP%\ahkbench\`。

### 4.2 生成对比报告

```bash
# 只生成（用当前 CSV）
python tools/ahk-bench/report.py

# 带历史轮次做多轮波动对比（推荐：把每轮目录先备份下来）
python tools/ahk-bench/report.py "$TEMP/ahkbench" \
    --prev <第1轮目录> <第2轮目录>
```

> 上例是 **Git Bash** 写法；PowerShell 下把 `"$TEMP/ahkbench"` 换成 `$env:TEMP\ahkbench`。

### 4.3 三个 Windows 陷阱（踩过，别改回去）

1. **输出路径必须由 `run.sh` 显式传给 AHK**（`AHK_BENCH_OUT`，Windows 路径）。
   Git Bash 的 `$TEMP` 与 Windows `%TEMP%` 可能不是同一个目录 ——
   不显式传，run.sh 会永远轮询不到哨兵文件。
2. **`AutoHotkey64.exe` 是 GUI 子系统进程**，直接调用不会等待。
   所以是后台拉起 + 轮询 `<id>.done` 哨兵，而不是依赖退出码。
   脚本内必须挂 `OnError` 守卫，否则未捕获错误会弹模态框导致静默挂起。
3. **AHK 脚本路径必须 `cygpath -w` 转 Windows 形式**。
   `/d/xxx` 会被 AHK 解析成 `D:\d\xxx`。

### 4.4 两条测量纪律（内存类基准必守）

1. **必须带阳性对照。** 先证明方法能测出已知泄漏（本仓库用「Map 持有自身」，
   实测残留 10,916 KB / 223.6 B每组），再谈被测对象有没有泄漏。
   没有它，「没测出来」和「没有泄漏」无法区分。
2. **必须每用例独立进程。** 同进程连续跑多用例时 AHK 自身分配会让基线漂移
   （实测 3216 → 4696 KB），残留量甚至会算出负值。

## 5. 三条必须知道的负面结论

这三条与「优化成功」相反，但它们同样是本次工作的产出 —— 写在这里是因为
**它们每一项都能省下一次无效的改动**。

1. **键名校验的正则优化没有收益（1.03×）。**
   单次调用本就只花约 1.35 µs，且发生在技能加载路径而非每 tick。
   **不要改。** 三份计划都不含这一项。

2. **定时器「忙等到点」不是「提升精度」。**
   p50 / p95 三者几乎无差别；可复现的收益只有尾部稳定性
   （`new` 稳定 0.17~0.23 ms，`old` 在 1.05~4.92 ms 摆动）。
   CPU 方面本机**未测出可复现差异**（两区间重叠）——
   **既不能说省 CPU，也不能说更耗 CPU。**

3. **「自引用闭包永久泄漏」的推断不成立。**
   先前依据代码走查推断 `skill_manager.ahk:329-379` 的 `executor.Bind(...)` 会永久泄漏；
   带阳性对照的实测显示：自引用闭包 444 KB vs 不成环对照 412 KB，**无差异，不泄漏**。
   真正泄漏的是**对象互指**（`skill_group.ahk:793-804`，19,956 KB / 408.7 B每组）。
   此项已从清单移除。

   > 注意：这不与 `docs/research/` 中「循环引用 100% 泄漏」的结论冲突 ——
   > 那条指的是**真正成环**的结构（本基准的阳性对照已复现：10,916 KB / 223.6 B每组），
   > 而 `executor.Bind(...)` 这个构造**并没有形成可到达的环**，属于判据用错而非规律失效。
> **补充（第四条，2026-09-14 新增）**：方案 C 的 T13「`#Include` 收敛降启动 ≥15 ms」
> **已证伪** —— 生产唯一被包含文件数只有 5，边际 825 µs/文件 → 收益上界 2.7~4.1 ms。
> 以及 T10 的原型实测带**口径警告**（只复刻了 4 次遍历中的 2 次，不可与 T6 的 1.80~1.96× 相乘）。
> 详见 [`plan-C-evaluation.md`](./plan-C-evaluation.md)。
> **补充（第五条，2026-09-14 新增）**：调度原型的「加速比随键数衰减」**不要去优化排序**。
> 消融证明衰减 100% 来自 `SeqSortPair`（占 collect 的 17% / 37% / 41%），但换**二路归并实测更慢**
> （m=8 慢 4.19×、m=13 慢 1.61×、m=38 慢 1.18×，AHK 常数项压过渐进优势），
> 且 K=24 时排序仅占一个定时器网格的 0.09%。
> 见 [`scheduling-bench` §4.1.1 / §4.1.2](./scheduling-bench-2026-09-14.md)。
> **补充（第六条，2026-09-14 新增）**：序列化「改成流式输出」没有收益 —— **O(n²) 前提不成立**。
> 字符数 4.10× 时耗时 4.12×（严格线性）；零中间字符串的 `stream` 与生产 `concat` 的
> 三轮区间完全重叠；`buf` 慢 46%、`parts` 慢 13%。瓶颈是 **0.24 µs/字符的解释器常数**，
> 不是拷贝量级。距目标 9.7× / 13.4× → **T9 取消**。
> 连带结论：**T1 的目标同样不可达**（实测 1.73~1.76×，目标却要 12.9×），
> 但 T1 本身白拿 43%，仍值得做 —— 只是目标值要改。
> 见 [`plan-C-evaluation.md` §5](./plan-C-evaluation.md)。
