# 方案 A · 保守重构（最小风险 · 单点替换）

> 三份方案（A 保守 / B 平衡 / C 深度）按**激进程度**划分，选型指南见
> [`README.md`](./README.md)，全部量化依据见
> [`bench-report-2026-09-14.md`](./bench-report-2026-09-14.md)。

---

## 0. 方案定位

**一句话**：只做**单个函数 / 单个点**内的替换与补守卫，不改变任何控制流、数据结构与模块边界。

| 维度 | 说明 |
|---|---|
| 改动面 | 4 个文件、6 处改动，全部为函数内替换或增补守卫 |
| 是否需要开关 | 否（每处改动都可在单个提交内独立回滚） |
| 预期周期 | 最短（无架构改动、无联调） |
| 适用场景 | 临近发布窗口；团队对 AHK 侧改动承受度低；需要先拿到确定收益再评估后续 |

**明确不做**（这些在方案 B / C 中）：

- 不动定时器主循环（`ahk_executor/sender.ahk` 的 `_ExecutePeriodic` / `_ExecuteSequence`）；
- 不做 tick 遍历合并（实测 1.8~2.0×，但要改热路径）；
- 不重写序列化层；
- 不引入新的模块、接口或配置项。

## 1. 优化目标与判定指标

### 1.1 量化指标

所有耗时用 **p50**（不是 max —— 见 §1.3）。基线取自本机三轮实测，见对比报告 §2.4。

| 编号 | 指标 | 定义与测量方法 | 当前基线 | 目标 | 判定方式 |
|---|---|---|---|---|---|
| M1 | JSON 序列化耗时 | 2 KB 配置对象序列化单次耗时 p50（QPC，30~60 次） | **1.29 ms** | **≤ 0.10 ms**（降幅 ≥ 90%） | 基准 `bench_json_escape` |
| M2 | 大字符串序列化耗时 | 8 KB 纯文本序列化 p50 | **5.44 ms** | **≤ 0.30 ms**（降幅 ≥ 90%） | 同上 |
| M3 | 异常守卫覆盖率 | 已知容错缺口中被守卫覆盖的比例 | **0/3** | **3/3** | 基准 `bench_stability` |
| M4 | 长跑内存残留 | 5 万次「创建并丢弃」后仍残留的私有内存 | **19.5 MB**（对象互指环） | **≤ 1 MB** | 基准 `bench_cycle_leak` |
| M5 | CPU 占用率 | 8 组 × 100 ms 周期定时器风暴下的进程 CPU | 20.7 ~ 25.0%（多轮区间） | **不劣化**（≤ 区间上限 + 2 pp） | 基准 `bench_timer_storm` |
| M6 | 启动时间 | AHK 进程墙钟（外部测量，含引擎初始化） | **164.33 ms**（empty，n=11） | **不劣化 ≥ 5%** | `tools/ahk-probes/bench_startup.py` |
| M7 | 回归基线 | AHK 全量用例 + Rust 全量 + 四闸门 | **见 test-map.md**（当前 697） | **不减少、不新增跳过** | `scripts/check-gates.sh` |

### 1.2 关于启动时间（M6）

启动成本里**进程创建本身就占绝大部分**：本机 `hostname.exe` 的空转基线为
144.85 ms（p50，Defender 扫描开销），AHK 空脚本为 **164.33 ms**（n=11，外部墙钟），
**引擎自身仅约 19 ms**。
因此：

- 本方案不做启动优化，只设「不劣化」门槛；
- 判定必须**先测 `hostname.exe` 基线再测 AHK**，否则会把 Defender 的波动误判成引擎回归；
- 复测入口：`python tools/ahk-probes/bench_startup.py 11`。

**留给方案 C 的一条实测线索**：`#Include` 的边际成本是 **673 µs/文件**
（实测 `inc_1000_x50` 相对 `empty` 增 35.19 ms / 50 个文件）。
也就是说**减少 `#Include` 数量**是启动优化里唯一有确定量级的杠杆 ——
脚本行数本身（解析 1.44 µs/行）反而很便宜。方案 C 的 T9 据此立项。

### 1.3 统计口径（三条硬性要求）

1. **用 p50 判定，不用 max。** `误差 max` 只是一个最坏样本，宿主一次抖动就改写它；
   实测同一变体的 `误差 max` 在多轮间可从 1.05 ms 变到 4.92 ms。
2. **P95 只在样本量足够时用。** `_Pct(arr,0.95)` 的索引是 `Ceil(n*0.95)`，
   n=54 时只容忍 2 个离群点；当离群幅度（约 15 ms 的一个调度网格）远大于阈值时，
   P95 会随机变红。**判断漂移用中位数。**
3. **结论必须跨轮可复现。** 单轮结论一律不作为验收依据（对比报告 §2.4）。

### 1.4 非目标

不追求 tick 路径提速、不追求降低 CPU、不追求缩短启动时间。这三项在方案 B / C 中处理。

## 3. 实施方案与风险评估

### T1 · JSON 转义快路径（P0）

**现状**：`_EscapeString` 逐字符 `SubStr(str,pos,1)` 取字符再 `result .= c` 拼接。
每次拼接都要重新分配并整串拷贝，是 O(n²)；实测 8 KB 文本要 5.44 ms（664.6 µs/千字符）。

**实现路径**：

1. 在函数入口加**快路径**：用 `InStr` 检查是否同时不含 `"`、`\` 与控制字符
   —— 不含则直接返回原串（真实配置里这是绝大多数情况）。
2. 需要转义时用 `StrReplace` 链式批量替换（`\` → `\\`、`"` → `\"`、`\n` → `\n` …），
   全程只产生常数次分配。
3. **保留旧逻辑作为兜底**：当字符串中出现快路径未覆盖的控制字符（如 `\x01`）
   时退回逐字符版本，保证输出与旧实现逐字节一致。
4. 等价性验证：对随机生成的字符串集合（含全部控制字符、Unicode、代理对）
   逐条比对新旧输出，要求 0 差异。**这一步是准入条件，不是可选项。**

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 快路径漏判某个必须转义的字符 | 输出与旧实现不一致 → IPC 协议解析失败或配置损坏 | 兜底路径 + 等价性用例（含全部 C0 控制字符与 `"` `\` `/`） |
| `RegExMatch` 判定控制字符本身变慢 | 抵消快路径收益 | 用 `InStr` 判定 `"`/`\`，控制字符交给 `RegExMatch`；**仅当快路径已命中才跳过** |
| 非 ASCII / Unicode 被误判 | 中文配置被二次转义 | 等价性用例必须包含中文、emoji（代理对）、U+2028/2029 |

**兼容性影响**：对调用方**完全透明**。函数签名不变、输出逐字节不变、无新增配置。

### T2 · 空数组越界 + 除零守卫（P0）

**现状**：`sender.ahk:573` `k := keys[step]` 与 `:580` `Mod(step, keys.Length)`，
`joystick.ahk:308` / `:314` 同型。当技能组为空（`keys.Length = 0`）时：
先抛 `Invalid index.`，即使过了这关也会 `Mod(x, 0)` 除零。
配置可经 IPC 传入 → **该异常在定时器回调里抛出，会直接中断整个 tick**。

**实现路径**：

1. 在取键前加长度守卫：`if !IsSet(keys) || keys.Length = 0`，直接返回（不发送、不重排）。
2. `Mod` 改为 `Mod(step - 1, keys.Length) + 1` 的写法前同样先判长度。
3. joystick 侧同型处理，并复用同一段守卫逻辑（两处代码形态一致，改法一致）。
4. 守卫命中时**记一条 WARN 并停止该组定时器**，而不是静默吞掉 —— 否则空技能组会变成
   「什么都没发生」的静默失败。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 守卫改变了原有「抛异常」的可观测行为 | 依赖该异常的调用方（若有）感知不到 | 改为显式 WARN 日志 + 停止定时器，可观测性更强 |
| 误伤 `keys.Length = 1` 的合法场景 | 单键技能组被当成空组 | 用例覆盖 0 / 1 / N 三种长度 |

**兼容性影响**：对合法配置无影响；对**非法配置**由「崩溃」变为「告警并停止该组」，
这是行为变更，需在发布说明中写明。

---

### T4 · 序列化递归深度上限（P0）

**现状**：`json_serializer.ahk:22-42` 的 `_StringifyValue` 有 `visited` **环检测**
（这点做得对），但**没有深度上限**。AHK 递归约 1200~1500 层会**直接终止进程，
且 try/catch 捕获不到**。而同项目的 parser 已有 256 的上限 —— 两边不对称。

**实现路径**：

1. 给 `_StringifyValue` 增加 `depth` 参数（默认 0），进入时 +1。
2. 超过上限（对齐 parser 的 **256**）时抛出**可捕获的**异常，消息中带上当前深度。
3. 顶层调用处不需要改签名（用默认参数），保证对外接口不变。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 上限设太低，正常深嵌套配置被拒 | 合法配置序列化失败 | 上限对齐 parser 已有的 256；用例验证 depth=255 通过、256 拒绝 |
| 新增参数破坏递归调用点 | 漏传 depth 导致计数失效 | 递归调用点全量核查（本文件内 4 处） |

**兼容性影响**：仅影响原本就会**崩溃进程**的输入。原本能成功的输入不受影响。

### T3 · `keyPressDuration` 入口夹紧（P1）

**现状与定性（务必读准）**：`executor.ahk:290` 从配置读 `keyPressDuration`（默认 15），
**不做上界校验**。发送侧靠 `sender.ahk:64` 的 `PRECISE_HOLD_MAX_MS := 20` 兜底，
但这一兜底分散在 `:513 / :574 / :722` **三个调用点各自判断**。
`_PressPreciseBatch`（`sender.ahk:426`）里的 `SleepUntil(plannedAt + kpd)` 是**阻塞式**的 ——
它现在安全，是因为三处调用点都记得判断；**新增第四个调用点一旦漏判就是无限阻塞**。

> 基准里「kpd=2000 阻塞 2 秒 / CPU 2296.9 ms」量化的是**这条约束被破坏时**的代价，
> **不是生产此刻正在发生的故障**。

**实现路径**：

1. 在 `executor.ahk:290` 读取后夹紧到 `[0, PRECISE_HOLD_MAX_MS]`。
2. 超出范围时**回落到默认值 15 并记一条 WARN**，而不是静默截断 ——
   静默截断会让用户以为配置生效了。
3. 保留发送侧三处判断（**不删除**）：入口夹紧是新的第一道防线，调用点判断是第二道；
   两者都在才构成纵深防御。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| 夹紧后原本「长保持」的用户配置失效 | 用户配了 kpd=500 想要长按，被改成 15 | 这是**当前已经发生的**行为（>20 本就走异步释放）；WARN 日志把它显式化 |
| WARN 刷屏 | 每次执行都记 | 同一配置项只在加载/变更时记一次，不在 tick 内记 |

**兼容性影响**：行为不变，但**新增了可见的 WARN**。需在发布说明中说明。

### T5 · 解除对象互指环（P1）

**现状**：`skill_group.ahk:793-804` 里 `capturedThis := this`，随后
`releaseTimer := () => (... capturedThis ...)`，最后
`this._releaseTimers[key] := releaseTimer`。
形成 `this → _releaseTimers → releaseTimer → capturedThis(=this)` 的环。
AHK 是**纯引用计数、无环检测**，成环即 100% 泄漏。

**实测**：闭环长度 2 的对象互指，5 万组残留 **19,956 ~ 20,016 KB**（408.7 ~ 409.9 B/组）；
同样结构但不成环的对照仅 304 ~ 332 KB（约 6.3 B/组），**相差约 65 倍**，三轮一致。

**实现路径**：

1. 不在闭包里捕获 `this`。改为：把释放动作抽成**独立的、不持有组对象引用的函数**，
   通过参数接收执行所需的全部数据（组 ID、键名、释放键）。
2. `_releaseTimers` 中保存的是该函数对象；组对象不再被闭包反向持有。
3. 在组销毁路径（`skill_group.ahk:711-714` 已有 `_releaseTimers.Clear()`）确认清理到位。
4. **必须补一条泄漏回归用例**：反复创建/销毁技能组 N 次，断言私有内存残留 < 阈值。

**风险点**：

| 风险 | 说明 | 缓解 |
|---|---|---|
| **改错导致按键不释放（最严重）** | 释放定时器拿不到数据 → 键卡在按下状态 | 用例必须覆盖：单键、多键同组、组被销毁时正在等待释放、释放定时器被覆盖（`:802` 的 `SetTimer(..., 0)`） |
| 闭包改签名后遗漏调用点 | 某条路径仍在用旧闭包 | 全量搜索 `releaseTimer` / `capturedThis`（本文件内 5 处） |
| 清理过早 | 组尚未销毁就清掉了定时器 | 保留现有 `_pendingReleases` 的守卫条件，只替换闭包构造方式 |

**兼容性影响**：对外接口不变。内部闭包结构变化，无外部可见差异。

### T8 · 错误限流桶加上界（P2）

**现状**：`error_system.ahk:43-44` 的 `_rateLastTime` / `_rateSuppressed` 两个 Map
以 `source` 为键，`:197-203` 只写入不清理 —— **不同 source 越多，Map 越大，永不收缩**。
这是慢速泄漏（每个新 source 只增加几十字节），但长跑进程 unbounded。

**实现路径**：

1. 给两个 Map 加容量上限（如 1024）。
2. 超限时按最久未使用淘汰（需要一个最近访问时间，可复用 `_rateLastTime` 本身）。
3. 淘汰时记一条 DEBUG，避免静默行为。

**风险点**：淘汰后该 source 的限流状态丢失 → **短时间内可能多写一条日志**。
影响有限（限流本就是尽力而为）。

| T1 | 空串、纯转义字符（`"""`、`\\\\`）、8 KB 以上长串、含 U+0000 的串 |
| T2 | **`keys.Length = 0`（核心）**、`keys.Length = 1`、`step` 越界 |
| T3 | `keyPressDuration` 为负数、非整数、极大值（2^31）、缺失（回落默认 15） |
| T4 | 深度 255 通过 / 256 拒绝；**自引用结构**（有 `visited` 环检测，应返回 `"<circular>"` 而非崩溃） |
| T5 | 连续创建销毁 10 万次后内存残留 < 阈值 |

### 5.4 异常分支

| 任务 | 异常 |
|---|---|
| T2 | 空组时**不抛异常**、记 WARN、停止该组定时器（断言三者同时成立） |
| T3 | 超限值时回落默认并**只记一次** WARN（不在 tick 内重复刷屏） |
| T4 | 超限值时抛出**可捕获**异常（断言能 `try/catch` 到，而不是进程终止） |
| T8 | 限流桶达到上限时不抛异常、不丢日志写入 |

### 5.5 性能压测

| 场景 | 判据 |
|---|---|
| 序列化：10 万次 2 KB 配置往返 | p50 达标 M1；**p50 漂移用中位数判定** |
| 定时器风暴：8 组 × 100 ms | CPU 不劣化（M5） |
| 长跑：技能组创建/销毁 10 万次 | 私有内存残留 < 1 MB（M4） |
| 长跑：错误日志 10 万条（不同 source） | `_rateLastTime` 容量不超上限（T8） |

## 6. 上线监控与回滚预案

### 6.1 关键监控指标与阈值

| 指标 | 采集方式 | 告警阈值 | 说明 |
|---|---|---|---|
| AHK 进程未捕获异常数 | 日志 ERROR 计数 | **> 0 即告警** | 改造后不应再有定时器回调抛出的未捕获异常 |
| 按键「按下未抬起」投诉/检测 | 前端状态 + 用户反馈 | **> 0 即告警** | T5 的最严重失效模式 |
| 序列化耗时 p50 | 周期性打点 | 超过基线 20% | T1 回归 |
| 进程私有内存 | 定时采样 | 8 小时内增长 > 50 MB | T5 / T8 泄漏 |
| CPU 占用率 | 定时采样 | 超过基线区间上限 + 5 pp | 兜底 |
| 限流桶容量 | DEBUG 计数 | 达到上限 | T8 生效 evidence |

### 6.2 回滚触发条件

满足**任一**条件即回滚：

1. 出现**按键按下不抬起**的确认案例；
2. AHK 进程崩溃率相对基线**上升**；
3. 序列化结果不一致（配置读取异常 / IPC 解析失败）；
4. 内存增长超过阈值且定位到本次改动引入的对象。

### 6.3 回滚步骤

本方案每个任务都是**独立提交**，因此回滚粒度是「任务」而非「整个方案」：

1. 定位失效任务（依据 §6.1 指标与 §6.2 条件）；
2. `git revert <该任务提交>`；
3. 跑四闸门 + 该任务相关的用例；
4. 重新跑对应基准，确认指标回到基线；
5. 发补丁版本，**不需要回滚整个方案**。

> 若 T1（P0）需要回滚，注意它是收益最大的一项，回滚后应立即复测序列化耗时，
> 确认回到 1.29 ms 而非更差（排除「回退不干净」）。
