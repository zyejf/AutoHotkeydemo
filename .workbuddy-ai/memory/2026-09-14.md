### 2. 真正的缺陷：测试统计口径错了

`_Pct(arr, 0.95)` 索引 = `Ceil(n*0.95)`，**n=7 时索引=7 → 断言的是最大值（P100）**，
宿主抖动一次就红。修正：

| 断言性质 | 统计量 | 样本量 |
|---|---|---|
| 端到端时延 P95 ≤ 20ms | P95 | 42 个（窗口 700ms → 4200ms） |
| 保持时长 == kpd | P95 | 20+ |
| **步进是否漂移** | **中位数** | 20+（漂移是系统性偏移，中位数即可检出，不被个别离群污染） |

另修 hybrid 用例：**旧写法把 `holds`/`steps` 存进 Map，同名键互相覆盖，最终只剩 1 个样本**
（等于单样本断言）。改为数组 + 中位数/P95。

### 3. 新测出的代价：精确定刻会连续占用 AHK 主线程

挂 5ms 探针定时器统计唤醒间隔（interval=100/kpd=15，3s）：

| 指标 | 实测 |
|---|---|
| 探针间隔 P50（定时器网格本身） | 16.08 ms |
| 探针间隔 P95 / 最大 | 43.98 / 47.47 ms |
| **扣除网格后最长连续占用** | **31.39 ms** |
| 占用占空比 | **29.2 %** |

原因：`SleepUntil` 中段用 `DllCall("kernel32\Sleep", 0)` 让出，**不会放行其它 AHK 定时器**
（AHK 定时器靠消息循环派发，回调内不泵消息）。后果：IPC 命令/热键最多被推迟 ~31 ms。
旧实现（`SetTimer(-kpd)` 异步释放）完全不阻塞 —— **这是用单线程忙等换亚毫秒精度的固有代价**。
暂未改（改「多段提前唤醒」可压到 ~16ms，但要多承担一次定时器抖动风险，而时延是首要需求）。

### 源码走查（T1–T6，6 条轨道）
- 启动链：`_tWinMain` → `LoadFromFile` → `InitForExecution` → `MainExecuteScript`；
  **热键在 auto-exec 之前生效**（`AutoHotkey.cpp:305`），**消息泵在 auto-exec 之后**（`:328`）。
- 解析：1 遍读行 + 3 趟后处理；**`#Include` 是解析期文本展开**（`script.cpp:3542`）并入同一条全局 Line 链表；
  只有「单操作数退化」，无算术折叠、无死代码消除。
- 执行：`Line` 双向链表 + `mJumpToLine` 预解析 → 跳转 **O(1)**；`Var` union + lazy 数字缓存；
  对象**纯引用计数、无 GC、无环检测**（`script_object.h:16-68`）；伪线程 = `g_array[]` 下标 + Line 游标（非 OS 线程）。
- 热键：hook 线程 `PostMessage(AHK_HOOK_HOTKEY)` → 主线程 `MsgSleep` 执行；回调**始终在主线程**。
- 消息循环：`GetMessage()` 阻塞（无 `MsgWaitForMultipleObjects`）；可中断阈值 17ms / 1000 行；
  引擎**主动放弃** `timeBeginPeriod`（`globaldata.h:213-215`）。
- 内存：SimpleHeap = 32KB bump 分配器，**只增不还**，析构从不被调用。

### 探针实测关键结论
- 启动 163.8ms，但本机进程创建基线（`hostname.exe`）就是 **144.9ms** → **引擎自身仅 ≈19ms**。
  解析 1.33µs/行；**`#Include` 592µs/文件**（与行数无关）。
- 15.625ms 网格坐实；**`timeBeginPeriod(1)` 完全无效**（gap 15.985→15.995）；**Sleep 断点在 21ms**（非 16ms）。
- **自旋期间消息泵未停摆**（`Sleep(0)` 驱动泵）：自旋 100ms 期间探针仍触发 7 次；真实代价是 gap p95 16.6→27ms。
- 热键时延 **p50 0.86ms**；**裸 SendInput（extraInfo=0）能触发 IL0/IL1/IL11 全部三档**
  → 坐实「Rust 侧下沉不可行」，`SendLevel(10)+InputLevel(11)` 挡不住它。
- 循环引用 **+22.9MB 全泄漏**（无环对照 +64KB）；1080 次热键注册 **+452KB 不回收**。
- 长路径 **30 038 字符正常**（无 MAX_PATH 限制）；CP936 会**静默丢字符**（长度不变）。
- OnError 返回 -1 继续 / 1 退出线程；**递归 1200 层 OK、1500 层终止且 `try/catch` 捕获不到**；
  **`#MaxThreads` 不丢弃并发定时器**（30/30 全跑）。

- **加速比随键数下降** 1.56×→1.32×→1.24×（8/24/64 键），瓶颈是 `SeqSortPair` 插入排序
  （K=64 大量键共用默认 50ms 间隔 → 同刻事件多 → O(m²)）。
- **T13 证伪**：生产唯一被包含文件数 = 5，`#Include` 边际复测 **825µs/文件**（旧记 673，该数在 673~825 波动）
  → 收益上界 **2.7~4.1ms**，远低于 M11「降 ≥15ms」。
- 裁决：**仍推荐方案 B**，但建议把「int µs 时刻表示」从 C 下沉到 B。

### ⚠️ 本阶段新坑（重要）
1. **漏写冒号的 legacy 赋值会静默挂起**：`firstDiff = "..."`（v2 里 `=` 是比较运算符，
   孤立比较语句触发 "no recognized action"）→ 加载期挂死、无 CSV、无弹框、exit=124。
   排查命令：`grep -nE '[^!<>=:+*/&|^.-]=[^=]'`。二分定位会得到**假阳性**（切在函数体的 `{` 上）。
2. **`rm` 被 safe-delete 钩子拦截**（genie-trash 无法处理 `/d/...` 与 `C:\...` 混写路径）
   → `.done` 哨兵删不掉 → 轮询立刻返回 0 秒 → **跑出上一轮陈旧 CSV**（r1/r3 全是假数据）。
   解法：**每轮独立输出目录**（`run_3rounds.sh` 已固化）。
3. **口径不一致会系统性低估 old**：B 阶段计时 `Collect` 而 A 阶段走 `CollectInto`
   （对 old 而言 = Collect + 拷贝），得出「两者相当」的错误结论。必须同口径 + 拆分 `NextDueUs`。
4. **场景写错则什么都没证明**：E 阶段分桶漂移第一版 tick 网格取 99.9ms（=慢键周期），
   快键每次落后 2 步被追赶逻辑吃掉 → old/new 都报 split=300/merged=0。改网格 = 快键周期 33.333ms
   后得到干净对照：**old merged=6/split=94，new merged=100/split=0**。
5. **`AutoHotkey64.exe` 无 `/version` 开关** → 改为跑极小脚本把 `A_AhkVersion` 写文件再读回。
6. **先测再优化**：原型 v1 反而慢 1.45×（热路径 4 次函数调用 + 每 tick 3 次分配）。
   只看 v1 会得出「整数化是负优化」的错误判断；三处优化（预夹紧 `st.iv`/内联饱和加法/零分配
   `CollectInto`）后才反转。

## 排序消融：把「加速比随键数衰减」定位到排序，并推翻自己的两条建议

### 起因
`plan-C-evaluation.md` §3.4 声称「衰减源于插入排序 O(m²)」但**没量化**，且给了两条建议。
先做消融验证，不照着猜测改。

### 做法
给 `PeriodicPolicy` 加仅供消融的 `st.noSort`（生产恒 `false`，关掉会破坏「按 dueUs 升序」契约），
`bench_seqgen.ahk` 新增 G 阶段，三轮跑（每轮独立输出目录）。

### 结果（三轮 median，p50 µs）
| K | sort=on | sort=off | 排序成本 | 占比 | old | 加速on | 加速off |
|---|---|---|---|---|---|---|---|
| 8 | 8.4 | 7.0 | 1.4 | 17% | 12.9 | 1.54× | **1.84×** |
| 24 | 37.7 | 23.9 | 13.8 | **37%** | 45.5 | 1.21× | **1.90×** |
| 64 | 111.4 | 65.5 | 45.9 | **41%** | 125.9 | 1.13× | **1.92×** |

**关掉排序后加速比恒为 ~1.9×，不再衰减 → 整条衰减曲线 100% 由排序造成。**

### ⚠️ 关键教训（可复用）
1. **单轮数据会误导**：第一轮 K=24 测出「排序占 16%」，三轮 median 是 **37%**。
   排序成本对「本轮同刻事件数」极敏感 —— 这类结论必须跨轮取中位数。
2. **先做廉价对拍再改库**：实现归并排序前先写 40 行独立探针（m=8/13/38/64 × 病态/随机各 3000 次）。
   结果**归并全面更慢**（m=8 慢 4.19×、m=13 慢 1.61×、m=38 慢 1.18×；只有 m=64 随机输入才 0.58× 反超）。
   若直接改库就白干了 —— AHK 是解释器，常数项压过渐进优势。
3. **「干脆不排序」是语义错误**：同一 tick 内不同键的 `dueAt` 可相差最多 `WAKE_LEAD_MS`(28ms)，
   生产按 `dueAt` 分桶后**逐桶在其到期时刻精确发送** → tick 内必须升序。
   只有**同桶内**（dueAt 完全相同）的顺序才无关。

### 新坑
- **AHK v2 的 Array 不能靠索引赋值自动扩容**：`sd[i] := x` 在 `i > Length` 时报
  "Invalid index"（只能写到 `Length+1`）。复用暂存数组必须先 `while sd.Length < m: sd.Push(0)`。
- 探针每轮新建数组会带来 GC 干扰，绝对值不可信（探针 m=38 报 162 µs vs 基准实测 46 µs）；
  **但同一 m 同一形态下的比值可靠**，结论只看比值。
- 原生 Windows Python **不认 Git Bash 的 `/tmp`**，glob 要写
  `C:/Users/fei/AppData/Local/Temp/...`（本次已踩第二次）。

### 结论
**不优化排序**：K=24 时 13.8 µs，而一个定时器网格 15,625 µs → 占 0.09%。
消融的价值是**解释**衰减曲线，不是消除它。
触发条件值得记：大量键共用同一间隔+同一原点时，它们的到期时刻永远相同却排在少数不同刻的键之后 →
插入排序退化成 O(m²) 搬移。若将来 K≥64 且同刻常态化，方向是**按 distinct due 分桶**（排 D 个值而非 m 个事件）。
