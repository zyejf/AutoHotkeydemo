### ⚠️ 两条新硬事实（已写入 AGENTS.md 定刻规范第 10 条）
1. **无 `SleepUntilUs` 兜底的调度路径，定时器周期必须 `Ceil` 不能 `Round`**。
   Round 向下取整 → 比计划时刻早醒 ≤0.5ms → 无键到期 → 再排 <1ms 定时器 →
   被 `Max(1,…)` 抬成 15.625ms 网格，白吃一格。实测 joystick 序列 3 秒漂移
   Round +15.1~+17.2ms → Ceil +1.9~+10.7ms。sender 用 Round 没事（有 28ms 提前量兜底）。
2. **`TIMING_EPSILON_US` 在「提前返回处不带容差」的结构下是死代码**：
   单键场景 `target == dueAt`，`target - now > 0` 提前返回后根本走不到 epsilon 判据。
   已从 joystick 删除（不设容差），判断是否到期的唯一判据就是 `target - now > 0`。

### ⚠️ 阳性对照（变异测试）抓到的两个假阴性 —— 值得复用
- 「基准重置为 now」的变异被**追帧分支覆盖 `last`** 屏蔽了：落后超过一个周期时
  `last` 会被重算。→ 必须**专门补一条非追帧路径**的用例（落后量 ∈ (interval, 2*interval)）。
- 「提前 5ms 视为到期」需要**同时变异两处**（提前返回条件 + 到期判据）才能复现，
  只改一处被另一处挡住 → 不红。
- 「Ceil→Round」内联在表达式里无法单测 → 抽成纯函数 `Joystick._NextPollMs(us)` 再断言。
  教训：**内联的取整/边界策略要抽成可测函数**，否则只能靠端到端。

## 缺口 #3 已闭合：T1 JSON 转义快路径（commit 20d3363）

`infrastructure/json_serializer.ahk` 的 `_EscapeString` 改为三段式快路径：
1. 不含引号 / 不含反斜杠 / 不含 0x00-0x1F → **原样返回**（配置与日志绝大多数字符串）

原逐字符实现保留为 `_EscapeStringCharByChar`：既是 `\uXXXX` 的兜底路径，也是测试 oracle。
实测收益 2KB 0.8776→0.4995 ms、8KB 3.5606→2.0600 ms（≈1.75×）。

测试：新增 `JSONSerializerEscapeTests`（7 例，注册在 `run_all_tests.ahk` 尾部注册块）。
全量 **664/664**（原 657，+7）。

## ⚠️ T11 上线即打脸：基线取自开发机是错的（commit b349dfb 修正）

推送后 CI 第一次真实跑（run 34932693789）就暴露问题：5 个 metric **全部落在 1.20~1.44×**
—— **GitHub 托管 runner 比开发机慢 30~40%**。结果：
1. 每次 CI 都刷满 5 条 WARN → **警告带永久失效**（狼来了）；
2. K=2.0 的可用余量被硬件差异吃掉 1.44× 中的大部分，比预估的薄。

**修正**：基线数值改为 **CI 实测中位数**，并在 `baselines.json` 记录 `_baseline_source` /
`_baseline_run`。同时给 `ahk-bench` job 加 `workflow_dispatch` 输入
`update_ahk_bench_baseline`：CI 上跑满 5 轮 `--update-baseline` 后把 baselines.json 作为
artifact 上传，**人工确认再提交**（基线是门禁锚点，不自动提交）。

**可复用结论**：
- **性能门禁的基线必须取自门禁实际运行的环境**，不是开发机。开发机与 CI 差 1.2~1.4×
  是常态，不是异常。
- 附带好处：判据只有上界 → 本地跑显示 0.7×（更快）不会失败，本地/CI 可以共存一份基线。
- 「警告带」要能用，前提是噪声地板远低于 warn_k；基线取错环境会直接让它失效。

### 追加：runner 池本身也有 ±10~17% 波动 → 基线要「居中」
改用 CI 基线后，相邻两次 CI 运行仍相差 **1.10~1.17×**（不是开发机差异，是 runner 池自身）。
单次运行的 p50 中位数当基线噪声太大，warn 带会偶发触发。
**修正**：基线取**两次独立 CI 运行的均值**（commit 89e1677）。
效果：第三次 CI 运行各 metric 落在 **1.04~1.07×**（此前最坏 1.17×），全部 PASS 无 WARN。

可复用结论：**性能门禁的基线既不能取开发机，也不能取单次 CI 运行** ——
后者只解决「环境不同」，不解决「同一环境池内的硬件代际差异」。
取多次独立运行的均值居中，是成本最低且效果明确的做法。
另：`workflow_dispatch` 的 `update_ahk_bench_baseline` 只上传 artifact、不自动提交 ——
基线是门禁锚点，必须人工确认。

CI run 34978303684 的 G3a 又红了一条：`tests::ipc_tests::test_roundtrip_latency`

| | 本机 | CI |
|---|---|---|
| 平均 | 69.4 μs | **2454.2** μs |
| 最小/最大 | 64.7 / 349 | 121.8 / **158073** μs |
| **P50** | 65.8 | **153.8** μs |

⚠️⚠️ **还原变异时的致命陷阱**：用 `shutil.copy2(bak, p)` 还原会**连 mtime 一起复制**，
使源文件 mtime 比变异构建产物更旧 → cargo 按 mtime 判定「无变更」→ **继续跑带变异的旧二进制**。
表现为「文件里明明没有 MUTATION，测试却还是红的」，极易误判成代码/环境问题。

## 追加：prod_escape 门禁误报的根因与归一化改造（commit 40cc24e + 9e057fa）

CI run 34981552999 的「AHK 生产基准门禁」红在 prod_escape（5 档 1.87~2.09×），
但该 PR 只改了 Rust IPC 统计口径与记忆文件，与 JSON 转义无关。

**定性（关键手法）**：5 个倍率挤在同一窄带 = 整机速度因子；若真是快路径退化，
全 ASCII 的 plain_* 会暴涨、本就走慢路径的 mixed/ctrl 几乎不动（倍率应严重分化）。
拉历史倍率序列确认 —— 同代码 5 次 CI 相对固定绝对值基线：

| run | 倍率 |
|---|---:|
| 34968820407 | 0.79~0.82× |
| 34975780100 | 0.92~0.96× |
| 34976964638 | 1.07~1.15× |
| 34978303684 | **0.52~0.53×** |
| 34981552999 | **1.87~2.09× FAIL** |

**跨 run 散布 3.7~3.9 倍**（历史文档记的「runner 池 ±10~17%」是严重低估，已更正）。
绝对值基线两头不讨好：慢机器上无变化也 FAIL；**快机器上真实 2× 回退读成 1.04× 而 PASS**。

**处置**：与 prod_tick 同机制加参考负载（预分配 Array 算术循环，REF_OPS=8192×REF_LOOPS=4
≈13ms/采样，紧邻每个 case），p50 改「批耗时÷参考负载耗时」；raw_ms 保留排障。
**gate.py 无需改动**（只认 metric 行 p50，info 行自动忽略）。
⚠️ 刻意不复用 prod_tick 的同名 RefBatch/MeasureRef：放进 _harness.ahk 会与 prod_tick
的本地定义重名（AHK v2 报重复定义），改 prod_tick 又会动到已有有效基线的基准。

**效果**：两次独立 CI 相差 1.018~1.101×（原 3.7~3.9×）；本地跑 CI 基线 1.00~1.17×；
最终 CI 8 档 **0.98~1.03× 全绿**。阳性对照：注入 T1 完全回退 → 4 条快路径档
**41.8~49.2× FAIL**，ctrl_512（未触碰的兜底路径）**0.99× PASS**。

**⚠️ 新坑：参考负载对 CPU 争用「过度校正」，方向向下所以安全。**
本机 20 满载进程（12 线程超订）：参考负载 +37~40%，而转义负载只 +0~43%
（payload 越大越偏内存/GC，对 CPU 争用越不敏感）→ 归一化值落到 **0.71~1.02×**。
即争用只会**压低**读数（不误报、但灵敏度下降）→ **别据此收紧 K**。
反推：CI 上 3.7~3.9× 的散布主要来自时钟/硬件代际（争用至多让转义动 1.4×），归一化对它是准的。

**K 按信噪比分别定**（不是统一值）：prod_escape **1.5 / warn 1.25**（信号 41~49×，
松一点换稳健性）；prod_tick **1.4 / warn 1.2**（信号仅 ~1.7×，再松就抓不住）。
