分档 P0 ≥10 / P1 5–10 / P2 2–5 / P3 <2，另有硬性升档（安全、误导性文档、阻塞他人、

### TD-018（新增 P1）：文档硬写 AHK 基线数字 → C3b 自动检查

方案 A/B/C + README 共 **8 处**硬写「642 / 642」，实跑总数早已 697。
「通过数 / 总数」把同一个数字硬编码两遍，测试一增长必然过期，且**过期后无人发现**
—— 它在文档里，不在代码里。

C3b 设计（走棘轮，不做硬阻断）：
- 扫 `docs/` 下 `.md`，找 `N / N`（两侧相同）形态，与 test-map 的
  `实跑总数（**N**）` 比对；
- 只认两侧相同的形态 → 不会误判「通过 697 / 失败 0 / 跳过 7」；
- 同行须含「通过/用例/测试/回归/套件/全量」之一 → 不会误判无关比例；
- 权威数字提取失败 → **硬失败**（检查失效不能靠棘轮蒙混）；
- 历史报告（带日期）里的快照合法，登记豁免 —— **改它等于篡改历史**。

### ⚠️ 两个新教训

1. **同一文件的多次 Edit 必须串行**。并行发两个 Edit 时，两者都基于同一旧快照各自写回，
   后写的覆盖先写的 —— 本次丢了 3 处改动（M7/M8 行、5.1 段、L23/L99），
   且工具**报 success**，只有事后 grep 才发现。改完同一文件必须 grep 复核。

2. **检查会触发它自己**。C3b 上线第一天就把台账里**描述 C3b 自身**的句子拦了：
   要解释「什么叫硬写 N / N」就得举一个 N / N 的例子，而例子必然是陈旧数字。
   解法：匹配前剔除反引号片段 —— 举例写在 `` ` `` 里，裸数字才拦。
   对照：裸 `555 / 555` 变红、反引号内 `444 / 444` 不检出，同时注入只新增 1 项。

## 阶段 2 第一项：TD-006 覆盖率棘轮门禁（已完成）

基线 **整体 81.64%**（命中 5206 / 总行 6377，15 个文件），逐文件数字在
`asd-tauri/docs/test-map.md`「覆盖率」节（该表是 `coverage-baseline.json` 的可读镜像）。

设计要点（`scripts/check-coverage.py`，CI 的 **G3f**）：
- **棘轮不设绝对值**。凭空定「≥80%」只有两种下场：一上线就红（逼出无断言的刷数
  测试），或低到形同虚设 —— 两种都比没有门禁更糟，因为它们**污染指标本身的可信度**。
- **双阈值**：整体 −0.5pp 防「总体稀释」，单文件 −2.0pp 防「丢车保帅」。
  阳性对照 2 证明了双阈值不是过度设计：小文件 100%→25% 时整体只跌 0.47pp，
  **只设整体阈值会完全漏掉**。
- **lcov 的 SF 是绝对路径**（本机 `D:\...`、CI `/home/runner/...`），
  必须归一化成 `<crate>/src/...` 才能跨平台比基线。
- 新文件只登记不判；基线里消失的文件（被删/改名）会被报出来。
- CI 的 coverage job 由 `continue-on-error` + 仅 push，改为**始终阻断**；
  `cargo install cargo-llvm-cov` 换成 `taiki-e/install-action`（预编译），
  否则「红灯与代码无关」会让门禁迅速被全员忽略。

### ⚠️ 端到端对照踩到的认知偏差
