## 阶段 2 第一项：TD-006 覆盖率棘轮门禁（已完成）

基线 **整体 81.64%**（命中 5206 / 总行 6377，15 个文件），逐文件数字在
`asd-tauri/docs/test-map.md`「覆盖率」节（该表是 `coverage-baseline.json` 的可读镜像）。

设计要点（`scripts/check-coverage.py`，CI 的 **G3f**）：
- **棘轮不设绝对值**。凭空定「≥80%」只有两种下场：一上线就红（逼出无断言的刷数
  测试），或低到形同虚设 —— 两种都比没有门禁更糟，因为它们**污染指标本身的可信度**。
- **双阈值**：整体 −0.5pp 防「总体稀释」，单文件 −2.0pp 防「丢车保帅」。
  阳性对照 2 证明了双阈值不是过度设计：小文件 100%→25% 时整体只跌 0.47pp，
  **只设整体阈值会完全漏掉**。
- **lcov 的 SF 是绝对路径**（本机 `D:\...`、CI `/home/runner/...`），
  必须归一化成 `<crate>/src/...` 才能跨平台比基线。
- 新文件只登记不判；基线里消失的文件（被删/改名）会被报出来。
- CI 的 coverage job 由 `continue-on-error` + 仅 push，改为**始终阻断**；
  `cargo install cargo-llvm-cov` 换成 `taiki-e/install-action`（预编译），
  否则「红灯与代码无关」会让门禁迅速被全员忽略。

## TD-019 冗余成员 Cargo.lock（已完成，commit `732c110`）

## ⚠️ 工具教训（本会话踩了两次）

1. **`io.open(p,'w', newline='\\n')` 会先截断文件再校验 newline** → 脚本报
   `ValueError: illegal newline value` 时文件已被清空（本会话把 check-tech-debt.py
   清成 0 字节，靠 `git checkout --` 恢复）。heredoc 里 `\\n` 会被原样传成
   `\\n`；要用 `'\n'`。**批量改文件一律写成 .py 脚本文件用 Write 落盘再执行**，
   别用 heredoc。
2. 批量 Edit 同一文件容易静默丢失 → 改用「Python 脚本 + 每个锚点 `assert count==1`」
   一次改完，锚点不唯一时**在写盘前**就失败，不会污染文件。

## TD-010 处置 vendored AHK 引擎（`AutoHotkey-2.0.26/`）

### C6 的两个口径（都是实测踩出来的）

1. **路径**用 git 自己的口径：`ls-files -s`（已跟踪）+ `ls-files --others --exclude-standard`
   （未跟踪但未被 ignore）。被 ignore 的本机产物（`AutoHotkey.exe`、`*.log`）**不管** ——
   它们只在本地存在，管了就「本地恒红、CI 恒绿」，那种门禁会被人学会无视。
   （第一版裸扫文件系统，多报了 18 个 ignored 产物。）
2. **内容**用**工作区**哈希 `git hash-object --stdin-paths`，**不是索引**。

   而那正是要防的，等进了索引错误已经提交出去了。
   `git hash-object` 与 .gitattributes 同一套归一化口径，实测与上游 sha 一致。

**阳性对照 3 组**：改工作区文件（不 add）→ 被改 1；移出已跟踪文件 → 被删 1；

**基线取自上游而非本地快照**：取本地快照的话，一旦本地已被污染，污染就会被固化进
基线、从此永远通过。校验的是「本地 == 官方」，不是「本地 == 本地上一次的样子」。

### 为什么 traits.rs 恒 0%（不是「忘了写测试」）

**trait 的默认方法体只为「实例化的具体类型」生成代码**。该文件定义的三个 trait

cargo-llvm-cov 测的是**测试二进制**，内联测试一并进分母。实测测试代码占比：

## Task #108 TD-016 收官：E2E「getTitle 超时」的真因与修复

### TD-030（P0 生产 BUG）：JSONSerializer 把数字 1/0 序列化成 true/false

起因是对 C1a 孤儿做定性时，顺手把 8 个 `tests/test_*.ahk`（TestReporter 独立脚本）
真跑了一遍 —— 报告里出现 `failed=true`。**接上执行就有回报**，与 TD-002 同型。

根因：`infrastructure/json_serializer.ahk:41`
`else if Type(value) = "Boolean" || value = true || value = false`。
**AHK v2 没有布尔类型**：实测 `Type(true)=="Integer"`、`(1 = true)==1`、`(0 = false)==1`。
于是 `Type(...)="Boolean"` 是死条件，而 `value = true` 对**任何整数 1** 成立。
实测：`Stringify(1)→true`、`Stringify(0)→false`、`Stringify([1,0,2])→[true,false,2]`、`Stringify(1.0)→true`。

爆炸半径（生产调用点）：`config_io.ahk:47` 配置写盘 / `backup_core.ahk:41` 备份 /
`ipc_channel.ahk:80,103` IPC 报文 / `webview2_manager.ahk` 十余处前端通信。

**关键实测（决定修法）**：用 `asd-domain` 的 example 跑 serde，双向都严格 ——
`bool <- 0` 报 `invalid type: integer 0, expected a boolean`；
`u64 <- false` 报 `invalid type: boolean false, expected u64`。
→ **不存在安全默认值**：一律输出数字会让 `allowOverlap: false` 变成 `0` 被拒；
一律按值判布尔又会让 `holdDuration: 0`（Rust `u64`，`validator.rs:858` 明确它是「无限保持」合法值）变成 `false`。
所以只能**按键名**判。

修法：`JSONSerializer.BoolKeys` 白名单（布尔字段是封闭集合、数值字段是开放的），
`_StringifyObject` 命中才输出布尔，并带 `!IsObject(value) && !(value is String)` 保护
（`success`/`error` 这些键也可能挂字符串或子对象 —— M5 变异证明这层保护是承重的，
去掉它会让既有 `Test_I16/I17/I20` 变红）。

- 先补测试再动刀：`JSONSerializerScalarTypeTests` 10 条，修前 6 红、修后 707/707。
- 阳性对照 5 组全红：恢复按值判布尔→6 红；删白名单一项→1 红；清空→3 红；布尔分支失效→3 红；去 `IsObject` 保护→3 红。

## TD-041 加固（提交 bdc47a5）：基准门禁超时重试

先纠自己的一个误判：报错文案写着「可能弹了模态错误框」，我据此推测是 AHK 弹框挂起 ——
核对后发现**所有 `bench_*.ahk` 都走 `_harness.ahk` 的 `BenchInit`，OnError 守卫默认就是开的**，
且没有任何一处传 `guard=false`。不是弹框。

真因在 `gate.py` 的两点：
1. `subprocess.Popen` 非阻塞启动 AHK，超时路径**没杀掉挂起的进程** —— 那个进程一直占 CPU，
   会污染后续轮次乃至后续 job 的计时。
2. 没有任何重试 —— 一次基础设施抖动就阻断合并。而这个 job 是「门禁不是信号」，
   偶发红直接挡 PR；重跑即绿又会训练人看到红先点重跑。

修法：超时先 `proc.kill()`，再重试 1 次（`ROUND_ATTEMPTS=2`）。
**只对超时重试，绝不重试回归判定** —— 后者重试等于给回归第二次蒙混过关的机会。

阳性对照（把常量压小就能测，很省事）：
- `ROUND_TIMEOUT=2` → 打印「第 1/2 次尝试超时…重试一次」→ FATAL → `SystemExit=2`，耗时 4.3s≈2×2s
- 恢复 300s → 单轮 13.2s 正常返回 CSV
（用 `importlib.util.spec_from_file_location` 直接加载 gate.py 再改模块常量即可，不用真跑 300s。）

### 又一个坑
MSYS 的 `/tmp` 对 Windows python 不可见；给 Windows python 传路径要用 `D:/...` 形式，
Git Bash 风格的 `/d/...` 会让 `CreateProcess` 报「系统找不到指定的文件」。

**结论：archive 里剩下 38 个不值得恢复**（18 要 GUI、20 无测试点），已写进台账免得后人重复试。

## TD-033：ToggleAll 停用用例加固（2026-09-17）

**先说复现结果**：连跑 20 次完整套件（改前 10 次 + 改后 10 次）**一次都没复现**那个 flaky。
所以这条不是「修好了某个 flake」结项的，而是把**结构脆弱性**消掉，并顺手暴露一个更隐蔽的问题。

原写法：`if GetActiveCount()=0 → ToggleAll()` 指望它激活，再 `ToggleAll()` 指望它停用 ——
而 `ToggleAll` 是**按「当前有无激活」自动选方向**的。第一次没激活成功，第二次就会走
「无激活 → 激活」分支，断言 `==0` 变成 `1 != 0`。前提成立与否取决于前面套件留下了什么。

改法：显式归零并断言为 0 → 逐个激活并读回真实激活数 → **有激活才断言 ToggleAll 清零，
没有就 `assert.skip` 并写明原因**（skip 进汇总，不会伪装成通过）。

### ⚠️ 关键细节：`SkillGroup.Toggle()` 有防抖

用 `ToggleGroup` 直接建前提时**必须先手动 `group._lastToggleTime := 0`** ——
`Toggle()` 里 `A_TickCount - _lastToggleTime < TOGGLE_DEBOUNCE_MS` 就返回 -1、什么都不做。
不重置的话激活数恒为 0，用例会「空转通过」而毫无察觉（我第一版就是这么写的，跑出来是 skip 才发现）。
`ToggleAll` 内部自己会重置，所以只有走 `ToggleGroup` 的路径才踩得到。

阳性对照：把 `ToggleAll` 改成空操作 → 立刻红 4 条（含本用例与 `Test_ToggleAll_ActivatesAllGroups`）。

## TD-043：Rust 并发用例在 Windows CI 上偶发失败（2026-09-17）

推送 TD-033 后 **CI 四闸门红了**，但失败**不在 AHK 侧** —— 是 G3a 里
`asd-application --test concurrency_tests` 的并发 `save_config_atomic`：

```
线程 save_config_atomic 失败: 配置错误: 重命名和复制均失败:
rename=Access is denied. (os error 5), copy=The system cannot find the file specified. (os error 2)
```

`gh run rerun --failed` 重跑即 success → flaky。**已排除与本次改动的关联**（那次提交只改 AHK 用例与文档）。

机理初判：`ConfigRepository::atomic_write` 的临时文件名是 `.tmp_{file}_{pid}_{nanos}`（唯一，不是碰撞），
但多线程最终 `fs::rename` 到**同一个目标路径** —— Windows 上目标被占用时 rename 返回 Access Denied，
回退的 `fs::copy` 又报源文件找不到。已登记 TD-043（P1）。

### 教训（重要，又踩一次）
**bash 里嵌 python 时，python 字符串中的反引号会被 bash 当命令替换执行并清空** ——
这次登记 TD-043 的整行反引号内容（`asd-application --test concurrency_tests`、`fs::rename` 等）全被吃掉，
插入的行变成了「| D flaky |  里的并发  用例在…」。**凡是内容里有反引号/引号/`$` 的，
一律先 `cat > $TEMP/x.py << 'PYEOF'`（带引号定界符）再执行**，不要用 `python -c "..."`。

## TD-043 修复：atomic_write 退避重试（2026-09-17）

按台账建议的 ①② 做：`rename` 改为**退避重试 4 次**（10/20/30ms，最坏多等 60ms）再走 copy 回退；
回退路径日志从 `debug!` 升到 **`warn!`**，让它成为可观测信号。

### 补了一条「能真正区分新旧实现」的测试（这才是重点）

用 Windows 的 `OpenOptionsExt::share_mode(0)`（**不共享任何访问**）独占打开目标文件，
稳定造出「目标被占用」这个瞬时冲突；再用 `mpsc::channel` 保证「已持住」之后才发起写盘，
避免测试自身变成竞态。`#[cfg(windows)]` 门控。

⚠️ **第一版阳性对照不成立**：我用 `File::open` 持文件，结果「把重试次数改成 1」也照样通过。
原因：**Rust 的默认 share mode 含 `FILE_SHARE_DELETE`** —— 那样持住的文件照样能被 rename 替换。
改成 `share_mode(0)` 后完美区分：重试=1 → rc=101，报的正是 CI 那个签名
（`重命名和复制均失败: rename=拒绝访问。 (os error 5), copy=另一个程序正在使用此文件…`）。
**教训：写并发/占用类测试时，必须先用阳性对照确认「坏实现真的会红」，否则测试是摆设。**
