### 交付

把 Rust 侧 `asd-domain` 已完成的 BUG-6（可疑配置值告警）对齐到 AHK 端，并拆除
阻碍落地的两处既有缺陷。5 个 commit：`d1e4b06`(feat infrastructure) →
`b67b221`(fix application) → `5670fbb`(feat presentation) →
`fc20fd5`(test) → `c502f04`(docs)，**已推送 origin/main**（累计 22 个）。

### 根因三层次（不只是「少一个告警函数」）

1. **主根因**：`config_validator.ahk` 只有「合法性」校验，没有「可疑性」诊断。
   按键数与时间序列不匹配、单位写错的超大间隔都被静默吞掉，直到运行时才暴露。
2. **次生根因（阻塞项）**：`Validate()` 本就可能返回纯 WARNING 数组，但
   `group_service.ImportGroups` 与 `webview2_manager._BridgeSaveSettings` 用
   `errors.Length > 0` 判定失败 —— **新增 WARNING 会直接放大这个既有隐患**，
   必须先拆除再补告警。
3. **三生根因**：WARNING 无任何可观测出口，只写一句「配置验证问题 N 个」，
   不含具体消息；补了告警用户也看不到。

### 关键实现决策（与 Rust 侧的三处刻意差异，已写入代码注释）

- 长度不匹配只在「序列 **多于** 按键」时告警（「少于」已由既有检查输出同义 WARNING）
- 超长值只覆盖 `(60000, 86400000]`（超过硬上界已由 ERROR 拦截，不重复）
- 子组下标 **1-based**（AHK 惯例；Rust 为 0-based，跨栈比对需 +1）

**热键长度分歧按用户决策维持现状**：AHK 15 字符即 ERROR，比 Rust 256 字符
WARNING 更严，语义已覆盖；不放宽既有校验阈值。

### 方案审查揪出的两个漏报缺陷（都已修 + 回归用例固化）

1. `_MakeSeries` 字段回退**不能用 `else if`** —— 子组 `pressKeys` 存在但非数组时
   （如空串）不会回退到 `keys`，整组漏检。必须用两个独立 `if`。
2. 超长值**不能只取全局最大值** —— `[70000, 90000000]` 会因最大值越过硬上界
   而被整体排除，导致 AHK 0 告警而 Rust 1 告警。改为 `_MaxNumberWithin(arr, ceiling)`
   先在合法区间内取最大值。

## 阶段八：按键触发链路 <20ms 延迟优化（分析完成，待需求对齐）

### 链路（7 段）与耗时定位

`物理按键` → ① AHK 钩子 `_OnHotkeyPress`（`hotkey_hook.ahk`，`InputLevel(11)`，亚毫秒）
→ ② Map 查找 + `OutputDebug` + `IpcClient.SendHotkeyEvent`（`ipc_client.ahk:485`）
→ ③ JSON 序列化 + 写命名管道 → ④ Rust `recv()` task → `mpsc(64)` → select 主循环
→ ⑤ `HotkeyMerger.push()` 入缓冲 → ⑥ **等 `flush_interval`（= merge_window = 100ms）才 flush**
→ ⑦ `outbound_tx.send()` → `spawn_ipc_listener`（`lib.rs:80`）→ `is_hotkey_registered`
→ `app_handle.emit("hotkey_event")` → WebView

**首要瓶颈 = ⑥**：`ipc.rs:579` `tokio::time::interval(merge_window)`，`merge_window` 取自
`HotkeyMerger::default()` = `HOTKEY_MERGE_WINDOW_MS = 100`（`hotkey_merger.rs:4`）。
事件到达时 `should_flush()` 通常为 false，必须等下一个 100ms tick → **平均 +50ms、最坏 +100ms**，
单这一项就是 20ms 预算的 5 倍。

### 丢事件的三个真实来源

1. **同键覆盖**：`HotkeyMerger.push()` 用 `buffer.insert(hotkey, msg)`，100ms 内同一热键按 N 次
   **只发 1 条**。现有测试在断言这个行为（`hotkey_merger.rs:123` "same hotkey should keep only latest"、
   `ipc.rs:890 test_hotkey_merger_same_key_overwrite`）—— 改语义必须同步改这两个测试。
2. `forward_to_outbound` 用 `try_send`，通道满则丢（`IPC_CHANNEL_CAPACITY=512`）。热键走
   `.send().await` 不丢，但其它消息丢。
3. `cleanup_connection`（`ipc.rs:672`）里 `merger.flush()` 的结果**直接丢弃**，断线时缓冲事件全丢。

### 澄清了用户的两个猜测

- **没有防抖/节流**：`ahk_executor/` 与 `src-tauri/src` 均无 debounce/throttle，
  唯一的"节流"就是上面这个 100ms 合并窗口（另有 `LOG_RATE_LIMIT_MS` 与日志有关）。
- **DOM 操作基本 N/A**：前端只有 `asd-tauri/src/{api.js,main.js,styles.css}`。
- `sender.ahk` 的 `SetTimer(timerFn, 10)` 属**发送侧**（按键模拟下发），不在上行链路；
  但若把"响应"定义为"完成一次模拟发送"，10ms 定时器粒度也要计入。

全局锁顺序 `ipc_manager` → `watchdog` 不可反转；`HotkeyMerger` 在 `Arc<Mutex<>>` 里（`ipc.rs:64`）。

### 新坑：推送重试要按 git 自身退出码判断

`git push ... | tail -3 && break` —— **`&&` 取的是 `tail` 的退出码（恒 0）**，
所以第一次失败也会 break，根本没重试。必须：

```bash
git push ... 2>&1 | tail -3
if [ "${PIPESTATUS[0]}" = "0" ]; then break; fi
```

本次实测第 3 次才成功（前两次 `CONNECT tunnel failed, response 502`）。
